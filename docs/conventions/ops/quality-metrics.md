# Метрики качества (Quality Metrics)

**Метрики качества (Quality Metrics)** — воспроизводимые числовые сведения об исходном коде, графе зависимостей и истории изменений. При код-ревью качество текущих правок оценивается прежде всего по изменению метрик относительно базовой ветки; абсолютный снимок даёт контекст состояния проекта. Основой цикломатической сложности служит [работа Маккейба](http://www.literateprogramming.com/mccabe.pdf).

## Общие правила

- Отчёт содержит полный снимок сырых `metrics` для всех доступных объектов; отсутствие сработавшего правила не должно скрывать объект из снимка.
- Схема отчёта имеет `schema_version: "1.0"`, а каждая вычисляемая метрика — версию её определения. Изменение формулы или состава учитываемых узлов повышает версию определения.
- Физический размер (`LOC` — Lines of Code) — число строк от объявления до закрывающей скобки объекта включительно: учитываются пустые строки и комментарии.
- Цикломатическая сложность (`CC` — Cyclomatic Complexity) метода равна `1 +` числу закреплённых точек ветвления. Набор учитываемых узлов (условия, циклы, `catch`, ветви `case` и `match`, тернарный и логические операторы) фиксируется тестами сборщика.
- Взвешенная сложность класса (`WMC` — Weighted Methods per Class) равна сумме `CC` всех объявленных методов; `max_cc` — наибольший `CC` метода класса.
- Несвязность методов четвёртого варианта (`LCOM4` — Lack of Cohesion in Methods 4) — число компонент связности графа нестатических методов. Методы соединены, когда используют одно свойство экземпляра или один вызывает другой.
- Нормализованный `LCOM4` равен `(components - 1) / (methods - 1)` при двух и более учитываемых методах. Для одного метода, интерфейса, абстрактного класса без реализации или неполных данных значение равно `null`.
- `null` означает «метрика неприменима или источник её не предоставил»; `0` означает измеренное отсутствие сущностей или связей. Нельзя заменять одно другим.
- Входящая (`Ca` — Afferent Coupling) и исходящая (`Ce` — Efferent Coupling) связанность считаются только по полному графу внутренних типов проекта: `Ca` — кто зависит от объекта, `Ce` — от кого зависит объект.
- Списки и ключи в отчёте сортируются детерминированно. Пути к файлам хранятся относительно корня проекта, идентификаторы типов — как полные имена.
- Универсальный балл качества и пакетные универсальные пороги не вводятся. Допустимые границы задаёт проект в `.coding-standard.php`; превышение создаёт `finding`, но не меняет код выхода.

## Зависимости

- Источник структуры и сложности должен анализировать синтаксическое дерево PHP; приблизительная сложность файлового счётчика не заменяет `CC` методов.
- Полный граф зависимостей предоставляет отдельный форматтер Deptrac. Маппинг «тип → модуль» сборщик строит по Composer `autoload` и `metrics.module_patterns` проекта. Диагностический отчёт только с нарушениями для этого не подходит.
- История Git для изменчивости (`churn`) необязательна: её отсутствие оставляет соответствующее поле `null`. Данные `scc`, статистика тестов и Clover XML обязательны для полного project-level отчёта.
- Внешний эталон на переходный период — PhpCodeArcheology 2.11.x; его `usedByCount` и `usesCount` нормализуются в `Ca` и `Ce`. Собственный сборщик обязан явно реализовать формулы этой страницы.

## Расположение

- **Входные артефакты:** отчёт анализатора, полный граф Deptrac и необязательные данные Git, scc и Clover передаются агрегатору отдельными путями.
- **Итоговые артефакты:** `var/metrics/` — зеркало включённых путей исходников. Корневой `var/metrics/report.json` агрегирует весь проект.
- **Отчёт каталога:** для каждого включённого каталога `X/` создаётся `var/metrics/X/report.json`; он агрегирует все включённые исходники своего поддерева.
- **Отчёт файла:** для исходника `X/Foo.php` создаётся `var/metrics/X/Foo.php.json`; он содержит метрики типов и методов этого файла.
- **Модули:** не имеют отдельного хранилища. Например, отчёт `src/Module/Billing/` хранится в `var/metrics/src/Module/Billing/report.json`, а часть модуля в веб-приложении — в `var/metrics/apps/web/src/Module/Billing/report.json`.
- **Модуль:** предметный компонент проекта, а не технический слой. В DDD-проекте это `{ProjectName}\Common\Module\{ModuleName}`; Domain, Application, Infrastructure и Presentation остаются внутренними слоями модуля. В этом пакете модули задаются согласованными группами `src/`.
- **Название модуля:** общий модуль получает префикс `Common`, модуль приложения — префикс его PSR-4-корня. Например, `Project\Common\Module\Billing` → `Common:Billing`, `Project\Web\Module\Billing` → `Web:Billing`, `Project\Api\v1\Module\Chat` → `Api/v1:Chat`.

Пример зеркала для структуры из [конвенции папок Symfony](../symfony-folder-structure.md):

```text
var/metrics/
├── report.json
├── src/
│   ├── report.json
│   ├── Application/
│   │   └── report.json
│   └── Module/
│       └── Billing/
│           ├── report.json
│           ├── Application/
│           │   ├── report.json
│           │   └── Service/
│           │       └── TBusinessPayment/
│           │           ├── report.json
│           │           └── SetPaymentStatusService.php.json
│           ├── Domain/
│           │   ├── report.json
│           │   └── Entity/
│           │       └── report.json
│           ├── Infrastructure/
│           │   └── report.json
│           └── Integration/
│               └── report.json
└── apps/
    └── web/
        └── src/
            ├── report.json
            └── Module/
                └── Billing/
                    ├── report.json
                    ├── BillingModule.php.json
                    └── Controller/
                        └── Payment/
                            ├── report.json
                            └── CancelController.php.json
```

Каждый путь после `var/metrics/` повторяет путь production-исходника от
корня проекта. Например, `src/Module/Billing/BillingModule.php` создаёт
`var/metrics/src/Module/Billing/BillingModule.php.json`, а отчёт папки
`src/Module/Billing/` — `var/metrics/src/Module/Billing/report.json`.

## Область анализа

- Корни production-кода определяются из секции `autoload` в `composer.json`; `autoload-dev` не входит в структурные метрики.
- `.coding-standard.php` содержит секцию `metrics`: `report_dir` и `report_layout: mirror` закрепляют зеркало исходников, `exclude` — список исключаемых путей, `module_patterns` — шаблоны расположения предметных модулей, `thresholds` — допустимые границы метрик. Этот конфиг является источником истины для сборщика.
- `exclude` применяется поверх корней Composer. В нём явно перечисляются `vendor/`, `.git/`, `var/`, `tmp/`, `packages/`, `migrations/`, `config/`, `docs/`, `public/`, `templates/` и `translations/`; проект дополняет список сгенерированным кодом внутри корня автозагрузки.
- `packages/` содержит самостоятельные пакеты, а не модули основного проекта. Их class-level и module-level метрики собираются отдельно из корня соответствующего пакета, если к нему подключён `coding-standard`.
- PHP-скрипты из `bin/` не входят в class-level, method-level и module-level модель, если Composer явно не объявляет их как production-исходники.
- `tests/` и `apps/*/tests/` не входят в распределения, `findings` и агрегаты качества production-кода. Их расположение и сьюты определяются конфигурацией PHPUnit и командами Composer; отдельно собираются только статистика тестов и покрытие.
- В зеркале сохраняется относительный путь от корня проекта, включая `apps/` и `src/`; исключённые каталоги не получают `report.json` и не создают пустые узлы.

## Модель отчёта

### Уровень метода

Для каждого объявленного метода записываются: полный идентификатор класса, имя метода, путь к файлу, физический `LOC`, `CC` и версия определения `CC`. Методы — компоненты класса: пара «класс → метод» показывает размер и сложность поведения.

### Уровень класса

Для каждого класса, интерфейса, перечисления или трейта записываются:

| Поле | Значение |
|---|---|
| `id`, `kind`, `file`, `module` | Полное имя, вид типа, относительный путь и предметный модуль |
| `loc`, `method_count`, `property_count` | Физический размер и состав типа |
| `wmc`, `max_cc` | Сумма и максимум сложности объявленных методов |
| `lcom4` | `components`, `normalized`, `method_count` и `definition_version` |
| `ca`, `ce` | Количество и отсортированный список полных имён входящих и исходящих типов |
| `churn` | Необязательное число коммитов и изменённых строк по файлу; при отсутствии истории — `null` |

Конструктор не участвует в графе `LCOM4`: внедрение нескольких зависимостей через продвигаемые свойства не должно искусственно связывать все методы. Статические методы, свойства и вызовы не учитываются, пока их правило не будет отдельно версионировано.

### Уровень модуля

Модуль — компонент верхнего уровня: его составляют классы и файлы, а связь между модулями образуют зависимости типов. Для каждого модуля записываются:

| Поле | Значение |
|---|---|
| `class_count`, `file_count`, `loc` | Количество классов, файлов и суммарный физический размер |
| `class_loc`, `wmc`, `max_cc` | Для каждого распределения: медиана, максимум, p90 и p95 |
| `internal_dependencies` | Число рёбер между разными типами одного модуля |
| `incoming_dependencies`, `outgoing_dependencies` | Количество межмодульных рёбер в модуль и из него |
| `external_dependency_share` | `outgoing_dependencies / (internal_dependencies + outgoing_dependencies)`; при нулевом знаменателе — `null` |
| `cohesion` | `internal_dependencies / (internal_dependencies + outgoing_dependencies)`; это графовая связность модуля, при нулевом знаменателе — `null` |
| `cycles` | Количество циклов, в которых состоит модуль, и отсортированные идентификаторы компонент сильной связности |
| `external_interface_size` | Количество публичных типов модуля, на которые ссылаются другие модули |

Перцентили вычисляются по отсортированному набору наблюдений линейной интерполяцией между соседними рангами; пустой набор даёт `null`. Медиана — p50. Входящие рёбра не включаются в долю внешних зависимостей: она описывает зависимости, которые создаёт сам модуль.

Средний `LCOM4` классов **не является** связностью модуля. `LCOM4` описывает граф методов одного класса, а `cohesion` модуля — долю его внутренних рёбер в графе типов.

### Уровень проекта

Корневой `var/metrics/report.json` агрегирует только production-код: количество
классов и файлов, суммарный `LOC`, число модулей, распределения `class_loc`,
`WMC` и `max_cc`, количество межмодульных зависимостей и циклы модулей. Он
содержит ссылки на отчёты первых каталогов зеркала, но не дублирует записи
всех классов и методов. Статистику тестов, покрытие и размер всей кодовой базы
добавляют отдельные источники project-level метрик. При доступности источников
корневой `metrics` также содержит:

| Поле | Значение |
|---|---|
| `codebase.languages` | Данные `scc` по языкам: `files`, `lines`, `code`, `comment`, `blank` |
| `codebase.modules` | Те же счётчики по `src/*`, `bin`, `tests` и `other`; требует запуск `scc` с `--by-file` |
| `tests.suites`, `tests.total` | Число тестовых файлов, строк и среднее число строк на файл по сьютам PHPUnit и всего |
| `coverage.lines`, `coverage.methods` | `total`, `covered`, `percent` из `clover.xml`; процент равен `null`, если объектов нет |

Статистика тестов, размер кодовой базы и покрытие — обязательные project-level
источники. Данные `scc` позволяют сопоставить структурные метрики production-кода
с общим числом файлов и строк проекта, а Clover показывает долю проверяемых
строк и методов. Отсутствующие обязательные секции не заменяются нулями.
`scc` устанавливают отдельно: `go install
github.com/boyter/scc/v3@latest` или используют готовый бинарник. Публичная
команда пакета сама создаёт `scc.json`, `test-stats.json`, `clover.xml` и
передаёт их агрегатору. Отсутствие обязательного инструмента или отчёта
завершает сбор ошибкой.

## Автоматизация и конфигурация

- Команда запускается из корня проекта-потребителя: `vendor/bin/coding-standard-metrics`. Если проект добавил `"metrics": "vendor/bin/coding-standard-metrics"` в собственный `composer.json`, используется `composer metrics`. Scripts установленного пакета Composer не наследует.
- Команда читает `composer.json`, `.coding-standard.php`, конфигурации Deptrac и PHPUnit текущего проекта; она не предназначена для анализа репозитория пакета `coding-standard`.
- Итоговые файлы создаются в `metrics.report_dir`: по умолчанию `var/metrics/report.json` и `var/metrics/index.html`. Каталог нужно добавить в `.gitignore` проекта.
- Сборщик и агрегатор формируют отчёт детерминированно по исходникам, полному графу зависимостей и `.coding-standard.php`. Агент только запускает команду и читает результат; вручную изменять JSON-артефакты нельзя.
- Реализация обязана валидировать `metrics.thresholds`: границы неотрицательны, доля находится в диапазоне от `0` до `1`, а неизвестные метрики и неверные типы завершают запуск понятной ошибкой.
- Формулы, обработка `null`, сортировка ключей, зеркальные пути и преобразование превышения границы в `finding` проверяются автоматическими тестами сборщика. Это инварианты кода, а не пункты ручного ревью.
- Проект задаёт в `metrics.thresholds` допустимые максимумы `LOC` и `CC` метода, размера и сложности класса, числа компонент `LCOM4`, `Ce`, доли внешних зависимостей и циклов модуля. Значения пересматриваются по распределениям и истории конкретного проекта.
- Превышение границы дополняет относительное ранжирование: `finding` содержит имя правила, настроенную границу и фактическое значение. `Finding` одного снимка не определяет результат ревью без сравнения с базовой веткой и проверки изменённого кода.

## Как используем

### Сырые метрики и находки

- Блок `metrics` хранит измерения без интерпретации и всегда остаётся машиночитаемым.
- Блок `findings` хранит неблокирующие кандидаты на анализ. Каждый элемент содержит `rule_id`, `subject` (вид и идентификатор объекта), `values` с исходными числами, `explanation` и версию правила.
- Правила находок используют относительное ранжирование внутри однотипных объектов, сочетания сигналов и границы из `metrics.thresholds`: крупный класс с несколькими компонентами `LCOM4` и большим `max_cc`; сложный метод; модуль с циклом или большой долей исходящих межмодульных связей.
- `findings` не меняют код выхода команды и не заменяют ревью. Границы меняются только в конфигурации проекта после проверки распределений и истории.

### Как читать отчёт ИИ-агенту

1. Сравните отчёт с базовым снимком той же версии схемы; важнее изменение показателя, чем одно значение.
2. Начинайте с методов с большим `CC` и `LOC`, затем проверьте класс по `WMC`, `max_cc` и `LCOM4`.
3. Класс с `LCOM4.components > 1` — кандидат на разделение обязанностей; сначала проверьте, не является ли он намеренным фасадом или классом интеграции.
4. Высокий `Ce`, рост `external_dependency_share` и цикл модулей — повод проверить границы и направление зависимостей. Высокий `Ca` допустим у стабильного публичного контракта, но повышает цену изменения.
5. Не делайте вывод только по одной метрике: сопоставляйте размер, сложность, связанность, изменчивость и покрытие. Отсутствующие необязательные данные не заменяйте нулём.

### Сравнение при код-ревью

1. Базовый снимок собирается для merge-base текущего изменения и целевой ветки; текущий снимок — для проверяемого HEAD.
2. Оба снимка собираются одной версией определений метрик и с одинаковой конфигурацией. Несовместимые снимки не дают нулевую дельту: сравнение завершается ошибкой с причиной.
3. Артефакт PR содержит оба исходных снимка, машиночитаемое сравнение и короткое резюме. HTML-дашборд может прикладываться дополнительно, но не является входом ИИ-агента.
4. Сравнение отдельно показывает изменённые, добавленные и удалённые методы, классы и модули. Рост общего `LOC` или числа объектов сам по себе не считается ухудшением.
5. ИИ-агент связывает регрессию с файлами текущего diff. Рост сложности, несвязности или внешней связанности, снижение покрытия и появление циклов требуют исправления либо явного обоснования в PR.
6. Необъяснённая регрессия в изменённой области является причиной не одобрять ревью. Отсутствие регрессии не заменяет проверку поведения кода и соблюдения конвенций.

Метрики дополняют конвенции для [сервисов](../core-patterns/service.md), [DTO](../core-patterns/dto.md), [сценариев использования](../layers/application/use-case.md) и [модулей](../modules/index.md), но не отменяют их правила ответственности и зависимостей.

## Пример

Корневой отчёт содержит только агрегаты всего production-кода и ссылки на
первые уровни зеркала. Например, `var/metrics/report.json`:

```json
{
  "schema_version": "1.0",
  "scope": {"kind": "project", "source_path": "."},
  "metadata": {"commit": "abc123", "generated_at": "2026-08-08T12:00:00Z"},
  "metrics": {
    "project": {
      "class_count": 2898,
      "file_count": 3592,
      "loc": 177222,
      "module_count": 20,
      "class_loc": {"median": 42, "max": 335, "p90": 122, "p95": 184},
```

## Чек-лист для проведения ревью кода

- [ ] В `.coding-standard.php` заданы и обоснованы `metrics.thresholds`; изменение границы проверено отдельно от изменения production-кода.
- [ ] Отчёт сгенерирован командой сборщика для текущего коммита; JSON-артефакты не редактировались вручную.
- [ ] В артефакте PR есть совместимые снимки merge-base и текущего HEAD, а также их машиночитаемое сравнение.
- [ ] Новые `findings`, превышения границ и изменения метрик сопоставлены с файлами текущего diff.
- [ ] Для каждого принятого риска есть решение: исправить код, обосновать исключение или изменить проектную границу отдельным изменением конфигурации.
- [ ] Рост сложности, несвязности или внешней связанности, снижение покрытия и появление цикла объяснены задачей и не скрыты ослаблением границы.
- [ ] Сопоставлены размер всей кодовой базы, объём тестов и покрытие; отсутствие обязательных данных `scc` или Clover завершает сбор ошибкой.
