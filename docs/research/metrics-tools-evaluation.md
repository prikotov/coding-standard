# Сравнение анализаторов метрик для `PHP`-проекта

## Определение и приоритет метрик

**Метрика кодовой базы** — количественный показатель, рассчитанный по исходному коду или связанным с ним данным: графу зависимостей, отчёту о покрытии, истории изменений. Метрика отвечает на вопросы «сколько?», «где больше?» и «как изменилось?», но сама по себе не является нарушением или оценкой качества. Проблемное место определяется по сочетанию значений, их динамике и контексту.

Классификация ниже задаёт границы планируемого сборщика и агрегатора.

### Точно нужны

Эти показатели необходимы для обратной связи до и после изменения кода.

| Метрика | Уровень | Зачем |
|---|---|---|
| Физический `LOC` | метод, класс, файл, модуль, проект | показывает размер и позволяет находить крупные элементы |
| Цикломатическая сложность | метод; сумма (`WMC`) и максимум по классу; распределения по модулю и проекту | локализует сложную логику и не скрывает её средним значением |
| Количество методов и свойств | класс; распределения по модулю и проекту | показывает размер интерфейса и состояния класса |
| `LCOM4` | класс; распределения по модулю и проекту | показывает кандидатов с несколькими несвязанными группами обязанностей |
| Входящие и исходящие зависимости (`Ca`/`Ce`) | класс, модуль | показывает, от чего зависит элемент и на какие элементы влияет его изменение |
| Внутренние и межмодульные зависимости | модуль, проект | показывает связанность модулей и степень их изоляции |
| Циклические зависимости | модуль, проект | выявляет взаимную зависимость, усложняющую независимые изменения модулей |
| Размер публичного интерфейса модуля | модуль, проект | показывает, какая часть модуля используется снаружи |
| Медиана, `p90`, `p95` и максимум основных показателей | модуль, проект | сохраняет распределение и выбросы, которые теряются в среднем значении |
| Покрытие строк тестами | метод, класс, модуль, проект | показывает, какая часть кода выполнялась тестами; отсутствие отчёта хранится отдельно от нулевого покрытия |
| Изменение показателей относительно базового отчёта | метод, класс, модуль, проект | даёт ИИ-агенту обратную связь о влиянии конкретного изменения |

Имена файлов, классов и модулей, вид элемента и списки рёбер также обязательны в отчёте, но это измеряемые объекты и данные для навигации, а не самостоятельные метрики.

#### Как читать обязательные метрики

У большинства метрик нет универсального «хорошего» числа. Сравнивать нужно однотипные элементы, распределение по проекту и изменение значения до и после правки.

| Метрика | Пояснение простыми словами | Как читать значение |
|---|---|---|
| Физический `LOC` | сколько строк занимает элемент вместе с пустыми строками и комментариями | больше — элемент крупнее, но не обязательно хуже; при одинаковой задаче обычно предпочтителен меньший размер, особенно важно не увеличивать выбросы |
| Цикломатическая сложность | сколько независимых путей выполнения создают условия, циклы и другие ветвления; последовательный метод без ветвлений имеет значение `1` | меньше — проще читать и тестировать; рост требует объяснения, высокие значения указывают на кандидата для упрощения |
| `WMC` и максимум сложности | `WMC` складывает сложность всех методов класса, максимум показывает самый сложный метод | уменьшение обычно хорошо; сумма характеризует класс целиком, максимум локализует самый трудный метод |
| Количество методов и свойств | сколько поведения и состояния собрано в классе | меньше обычно означает более узкую ответственность; большое значение — повод проверить класс, но не самостоятельное нарушение |
| `LCOM4` | на сколько не связанных друг с другом групп распадаются методы класса | `1` означает одну связанную группу; значение больше `1` — сигнал, что класс может совмещать несколько обязанностей; для нормализованного варианта лучше значение ближе к `0` |
| `Ca` | сколько внутренних классов зависит от данного класса | большое значение означает высокую цену его изменения; уменьшать его любой ценой не нужно, потому что у общего стабильного контракта оно закономерно высокое |
| `Ce` | от скольких внутренних классов зависит данный класс | меньше обычно означает более слабую связанность и более простой перенос; рост — повод проверить необходимость новых зависимостей |
| Внутренние и межмодульные зависимости | сколько связей остаётся внутри модуля и сколько пересекает его границы | меньшая доля межмодульных связей обычно означает лучшую изоляцию; допустимость каждой связи определяется конвенциями `Deptrac` |
| Циклические зависимости | образуют ли модули замкнутую цепочку зависимостей | `0` циклов — целевое значение; появление нового цикла считается ухудшением |
| Размер публичного интерфейса модуля | сколько классов модуля используется другими модулями | меньший интерфейс обычно проще сохранять стабильным; сокращать его ценой лишних обёрток не требуется |
| Медиана, `p90`, `p95` и максимум | медиана описывает типичный элемент, а процентили и максимум — наиболее крупные или сложные элементы | для размера и сложности уменьшение верхних значений обычно хорошо; рост медианы показывает системное изменение всего модуля или проекта |
| Покрытие строк тестами | какая доля исполняемых строк была выполнена во время тестов | выше обычно лучше; снижение требует проверки, но `100 %` не доказывает качество тестов и не является самоцелью |
| Изменение показателя | разница между текущим и базовым отчётом | собственного направления нет: рост сложности, связанности и циклов обычно плох, рост покрытия обычно хорош, изменение размера оценивается в контексте задачи |

### Могут понадобиться

Эти показатели могут усилить анализ, но первая версия полезна и без них:

| Метрика | Что может показать | Как читать значение |
|---|---|---|
| Частота изменений и число изменённых строк из `Git` | какие части проекта меняются чаще других | большое значение не является плохим само по себе, но усиливает риск крупного, сложного или слабо покрытого элемента |
| Нестабильность модуля `I = Ce / (Ca + Ce)` | насколько модуль зависит от других по сравнению с тем, сколько модулей зависит от него | ближе к `0` — модуль более стабильный, ближе к `1` — более зависимый; желаемое значение определяется ролью модуля |
| Глубина наследования и число потомков | насколько велика иерархия наследования и сколько классов зависит от базового поведения | меньшие значения обычно проще; большие требуют проверки, но допустимы для осознанной иерархии |
| Когнитивная сложность | насколько трудно человеку проследить поток выполнения с учётом вложенности | меньше — лучше; полезна, только если даёт дополнительный сигнал по сравнению с цикломатической сложностью |
| Покрытие ветвей | какая доля вариантов условий была выполнена тестами | выше обычно лучше и даёт более строгий сигнал, чем покрытие строк, но требует поддержки со стороны инструмента покрытия |
| Количество, результат и время тестов | объём набора тестов, наличие ошибок и стоимость его запуска | целевое число ошибок — `0`, время желательно уменьшать; количество тестов не имеет направления и не доказывает их качество |
| Частота совместных изменений файлов | какие файлы обычно меняются одним коммитом | высокая частота может указывать на скрытую связанность; уменьшение не является самостоятельной целью |
| `PageRank` графа классов | какие классы занимают центральное место в графе зависимостей | большое значение означает важность и риск изменения, а не хорошее или плохое качество |
| Доля абстракций и расстояние от главной последовательности | соответствует ли соотношение абстрактных и конкретных типов связанности модуля | меньшее расстояние считается предпочтительным в исходной модели, но применимость к архитектуре проекта ещё не подтверждена |
| `RFC` и `CBO` | сколько поведения может быть вызвано через класс и со сколькими типами он связан | меньше обычно проще; метрики нужны только при недостаточности уже сохранённого графа зависимостей |

Добавлять такую метрику следует только вместе с вопросом, на который она отвечает, и примером решения, которое изменится после получения значения.

### Точно не нужны

- набор метрик Холстеда и производные оценки времени разработки и количества ошибок;
- индекс поддерживаемости (`MI`), смешивающий размер, сложность, Холстеда и комментарии в одно число;
- формула дефектов Кана и метрики Карда—Агрести;
- `LLOC` как второй обязательный показатель размера наряду с выбранным физическим `LOC`;
- несколько вариантов `LOC`, `CC` или `LCOM` одновременно;
- количество тестов как самостоятельное доказательство качества класса или метода;
- единый «балл качества», скрывающий исходные показатели и причину изменения оценки.

Универсальные пороги также не считаются метриками. Предупреждающие и блокирующие значения можно вводить только после проверки распределений на реальных проектах.

## Контекст

Для инициативы по метрикам поддерживаемости требовался анализатор, из машинного отчёта которого можно построить единую модель уровня класса:

- `LOC` и `LLOC`;
- `LCOM`;
- афферентная и эфферентная связанность (`Ca`/`Ce`);
- цикломатическая сложность (`CC`);
- количество методов и свойств.

Это первоначальный список для сравнения готовых инструментов. По результатам исследования в обязательной модели оставлен один показатель размера — физический `LOC`; параллельный `LLOC` не отвечает на отдельный вопрос.

Оценивались `PhpMetrics`, `PDepend` и `PhpCodeArcheology`. Цель исследования — проверить инструменты на реальном коде пакета и выбрать основу для последующего агрегатора, а не сравнить возможности только по документации.

Первичное исследование выполнено 6 августа 2026 года в рамках `TASK-metrics-tools-evaluation`. Поиск альтернатив и проверка `scc` выполнены 7 августа 2026 года после обсуждения отчёта.

### Проверки

1. Каждый практически проверяемый анализатор запущен на полном каталоге `src/` проекта `TasK/Development`.
2. Проверено количество успешно обработанных файлов.
3. На пяти знакомых классах маленького контрольного пакета сопоставлены `LOC`/`LLOC`, `LCOM`, `Ca`/`Ce`, `CC`, методы и свойства:
   - `DtoStructureSniff`;
   - `ServiceStructureSniff`;
   - `EnumStructureSniff`;
   - `CrossModuleDomainRule`;
   - `ServiceContractDependencyRule`.
4. Отдельный минимальный пример проверял разбор атрибута `#[Attribute]`, конструкции `final readonly class` и продвигаемых свойств конструктора.
5. Для каждого кандидата оценены машинный формат, полнота полей уровня класса, лицензия и актуальность разработки.

Это проверка пригодности для выбранного сценария, а не доказательство корректности всех формул анализаторов.

### Интерпретация расхождений

- Одинаковые названия метрик не гарантируют одинаковую формулу или единицу подсчёта.
- `PhpMetrics` считает `loc` не как физический диапазон строк класса. `PDepend` и `PhpCodeArcheology` показали физический диапазон от объявления до конца класса.
- Определение `LLOC` у `PDepend` заметно отличается от двух других инструментов.
- `CC` и `WMC` не взаимозаменяемы, поэтому их значения нельзя сравнивать как одну метрику без нормализации определений.
- `LCOM` `PhpMetrics` и `PhpCodeArcheology` совпал на всех пяти проверенных классах.
- Для `CrossModuleDomainRule` `PhpCodeArcheology` показал четыре исходящие зависимости — по числу четырёх используемых внешних типов. `PhpMetrics` и `PDepend` показали три. Это частная ручная проверка, а не гарантия общей точности расчёта связанности.
- Во всех пяти классах `Ca` равен нулю: другие классы из анализируемого `src/` на них не ссылаются. Этот набор не проверяет поведение инструментов на ненулевом `Ca`.

## Оценка кандидатов

### `PhpMetrics`

Плюсы:

- зрелый инструмент;
- компактный `JSON`;
- присутствуют `LCOM`, `Ca`/`Ce`, `CC` и количество методов;
- успешно разобрал код пакета на `PHP` 8.4.

Ограничения:

- в `JSON` уровня класса нет количества свойств;
- семантика `LOC` отличается от физического количества строк;
- для полной целевой модели агрегатору потребовался бы второй источник или собственный разбор свойств.

### `PDepend`

Плюсы:

- зрелая модель структурных метрик;
- присутствуют `LOC`/`LLOC`, `Ca`/`Ce`, `WMC`, методы и свойства;
- успешно разобрал код пакета на `PHP` 8.4.

Ограничения:

- нет `JSON`-отчёта: доступен `XML`;
- нет `LCOM` в полученном отчёте уровня класса;
- стабильный релиз заметно старше релизов других кандидатов;
- закрывает целевую модель только вместе с дополнительным анализатором.

### `PhpCodeArcheology`

Плюсы:

- единственный проверенный `JSON`, содержащий все требуемые поля уровня класса;
- количество методов и свойств доступно напрямую;
- `LCOM` совпал с `PhpMetrics` на выбранных классах;
- отчёт также содержит метрики истории `Git` и дополнительные данные, полезные следующим задачам эпика;
- успешно разобрал код пакета и отдельный пример `PHP` 8.4.

Ограничения:

- проект моложе конкурентов;
- `JSON` значительно объёмнее необходимой агрегатору модели;
- пакет является плагином `Composer` и требует явного разрешения в `allow-plugins`;
- первый запуск 2.11.3 интерактивно запрашивает подтверждение изменения формул, введённого в 2.7.0;
- поля связанности называются `usedByCount` и `usesCount`; их соответствие принятым в проекте `Ca`/`Ce` нужно явно закрепить в модели метрик.

- `scc` на два порядка быстрее анализаторов синтаксического дерева, но собирает существенно более простую модель уровня файла.

- `PhpCodeArcheology` требует больше всего памяти и создаёт самый крупный отчёт, но его 22 секунды остаются приемлемыми для локальной команды и периодического запуска в `CI` на проекте такого размера.
- Время нельзя сравнивать отдельно от полноты результата: `scc`, `PHPLOC`, диагностические анализаторы и анализаторы уровня класса решают разные задачи.

`php-linter`, `PHP Stability Metrics` и `PHPMD` не включены в таблицу времени. Для `php-linter` нет аргумента каталога: он требует установки непосредственно в анализируемый репозиторий и проверяет все отслеживаемые файлы, поэтому его запуск изменил бы условия теста. Два остальных инструмента не предоставляют сопоставимую полную модель и требуют отдельной конфигурации правил или компонентов.

### Практическая проверка `scc`

`scc` написан на `Go`. Проверена стабильная версия 3.7.0, установленная командой `go install github.com/boyter/scc/v3@latest`.

```bash
scc -a --by-file -i php -f json ~/MyProjects/TasK/Development/src
```

Результат для `src/`:

| Показатель | Значение |
|---|---:|
| Файлы | 3 592 |
| Физические строки | 177 266 |
| Строки кода | 133 785 |
| Строки комментариев | 15 373 |
| Пустые строки | 28 108 |
| Оценка сложности | 5 697 |
| Уникальные строки (`ULOC`) | 51 006 |
| Размер | 5 647 510 байт |

`scc` не строит синтаксическое дерево. Он распознаёт код, комментарии и строки конечным автоматом, а сложность оценивает по встреченным ветвлениям и циклам. Поэтому показатель сложности пригоден для быстрого ранжирования файлов одного языка, но не должен подменять `CC`, рассчитанный анализатором синтаксического дерева.

Вывод: **`scc` полезен как отдельный источник метрик уровня проекта и файла, но не является альтернативой `PhpCodeArcheology` для модели уровня класса**. Он соответствует назначению отдельной задачи `TASK-metrics-codebase-size`.

Операционное ограничение: `scc` не является зависимостью `Composer`. Для воспроизводимого запуска потребуется закреплённый внешний бинарник, контейнер или установка через `Go`; версия 3.7.0 требует `Go` 1.25 при сборке из исходников.

### Практическая проверка `Phanalist`

`Phanalist` обработал 3 592 файла и вернул 12 935 диагностик для 3 151 файла. На маленьком контрольном пакете правило низкой сцепленности сообщило для пяти классов `LCOM4`: 3, 3, 4, 6 и 8 соответственно. Эти значения нельзя напрямую сравнивать с полем `lcom` других инструментов без фиксации формулы.

При установке пакет имел версию 1.1.10, но загруженный исполняемый файл сообщил версию 1.1.1. Это отдельный риск воспроизводимости упаковки, который нужно перепроверить перед возможным внедрением.

Главное ограничение для агрегатора: метрики находятся в аргументах диагностических сообщений и появляются только при срабатывании правила. Это удобно для контроля качества, но не для полного регулярного снимка всех классов.

### Практическая проверка `php-dep`

`php-dep` обработал 3 592 файла, нашёл 3 589 внутренних объявлений, 4 140 узлов и 22 274 ребра; сформировал три предупреждения. На маленьком контрольном пакете количество исходящих зависимостей пяти проверяемых классов равно 4, 2, 2, 4 и 4; входящих — нулю.

Инструмент интересен как независимый источник графа: каждое ребро содержит тип отношения, файл, строку и оценку уверенности. Однако пакет доступен только из ветки `main`, имеет небольшую пользовательскую базу и не измеряет сцепление или сложность. Постоянная зависимость сейчас не оправдана; повторную проверку можно провести после появления стабильного релиза.

### Практическая проверка `PHP Insights` и `PHPLOC`

`PHP Insights` успешно сформировал `JSON` со сводными оценками: качество 61, сложность 91,5, архитектура 64,7, стиль 73,5 и ноль проблем безопасности. Остальная часть отчёта — 18 657 найденных нарушений по категориям, а не сырые метрики всех классов.

`PHPLOC` 8.0.7 обработал 3 592 файла и сообщил 177 222 физические строки, 24 866 логических строк, 2 898 классов, 445 интерфейсов, 12 трейтов и 9 749 методов. Встроенная строка версии исполняемого файла при этом осталась 8.0.6. Его `JSON` содержит только агрегаты проекта: минимумы, средние, максимумы и общие количества. Разница в 44 физические строки с `scc` подтверждает, что даже базовый показатель зависит от правил подсчёта. Для статистики уровня проекта инструмент пригоден, но `scc` не зависит от версии `PHP`-парсера и покрывает весь многоязычный репозиторий.

## Вариант собственного сборщика

### Зачем рассматривать

`PhpCodeArcheology` решает более широкую задачу, чем требуется эпику: его полный отчёт на `TasK/Development` занимает 55,1 МБ, а процесс — 524 МиБ памяти. Агрегатору нужна небольшая стабильная схема, точные определения формул и несколько графовых агрегаций.

Собственный сборщик не означает написание парсера языка. Разумная основа — прямая зависимость `nikic/php-parser` 5.x: библиотека строит синтаксическое дерево `PHP` 8.4, сохраняет позиции узлов, предоставляет обход дерева и разрешение полных имён. Она уже присутствует в дереве зависимостей, но для собственного кода должна быть объявлена напрямую.

Предлагаемая цепочка:

1. `nikic/php-parser` один раз разбирает каждый файл и собирает размер, состав классов, методы, свойства, сложность и данные для сцепления методов.
2. `Deptrac` остаётся источником разрешённых зависимостей между классами и модулями; дублировать его правила собственным неполным поиском типов не нужно. Штатный формат `JSON` содержит диагностики, но не полный граф разрешённых связей, поэтому потребуется небольшой собственный форматтер `Deptrac`, выводящий все категории рёбер.
3. Собственный агрегатор сопоставляет классы модулям по закреплённой конфигурации, инвертирует полный граф зависимостей, считает входящие и исходящие связи, циклы и агрегаты модулей.
4. `Clover XML` используется для обязательной метрики покрытия, если проект формирует такой отчёт; отсутствие отчёта обозначается как `null`. История `Git` остаётся необязательным источником.
5. Сборщик сразу пишет `report.json` в формате проекта, без промежуточного отчёта на десятки мегабайт.

### Вопросы к обязательным метрикам

Набор выбран по принципу «цель → вопрос → метрика»: поле включается, только если отвечает на вопрос о поддерживаемости или помогает найти место для рефакторинга.

| Вопрос | Обязательные метрики | Зачем |
|---|---|---|
| Где находится крупный компонент? | файл, полное имя, вид, модуль, физический `LOC`, количество методов и свойств | базовый размер и навигация; простые и проверяемые значения |
| Какой метод трудно читать и тестировать? | `LOC` и цикломатическая сложность каждого метода; максимум и сумма по классу | локализует сложность, а не прячет её в среднем класса |
| Выполняет ли класс несколько несвязанных задач? | число компонентов связности методов `LCOM4` и нормализованное значение | показывает кандидатов на разделение класса |
| От скольких классов зависит класс и сколько классов зависит от него? | списки и количества уникальных внутренних входящих/исходящих зависимостей (`Ca`/`Ce`) | списки объясняют число и позволяют воспроизвести агрегации |
| Соблюдаются ли границы модулей? | внутренние, входящие и исходящие межмодульные рёбра; циклы; размер используемого снаружи интерфейса | обнаруживает архитектурную связанность и точки риска изменений |
| Где сосредоточен риск в модуле? | количество классов/файлов, суммарный `LOC`, медиана, `p90`, `p95` и максимум размера и сложности | распределение устойчивее среднего и сохраняет выбросы |
| Какая часть элемента выполнялась тестами? | покрытие строк метода, класса, модуля и проекта | дополняет структурный риск данными о выполнении кода тестами |
| Как изменение повлияло на кодовую базу? | разница обязательных показателей между базовым и текущим отчётом | даёт обратную связь по конкретному изменению, а не только снимок проекта |

Метрики метода обязательны: заявленный уровень «метод → класс» нельзя достоверно представить только одним `CC` класса. В отчёте класса нужны как минимум сумма сложности методов (`WMC`) и максимальная сложность метода; среднее без максимума скрывает проблемный метод.

### Формулы первой версии

Для каждой метрики нужно закрепить точное определение и примеры с ожидаемым результатом. Одинаковые имена у существующих инструментов уже дали разные числа.

| Метрика | Определение первой версии |
|---|---|
| Физический `LOC` | число строк исходного файла; для класса или метода — `endLine - startLine + 1`; включает пустые строки и комментарии внутри диапазона |
| Цикломатическая сложность метода | `1 +` количество явно перечисленных точек ветвления; перечень узлов `if/elseif`, циклов, `catch`, ветвей `case/match`, тернарного оператора и логических операторов закрепляется тестами |
| `WMC` класса | сумма цикломатической сложности объявленных в классе методов |
| `LCOM4` | проектный вариант: число компонентов связности не статических методов; методы соединены, если обращаются к одному свойству экземпляра или один вызывает другой |
| Нормализованный `LCOM4` | `(components - 1) / (methods - 1)` для двух и более учитываемых методов; иначе `null` |
| `Ce` класса | число уникальных внутренних классов, от которых класс зависит |
| `Ca` класса | число уникальных внутренних классов, которые зависят от класса |
| Доля внешних связей модуля | исходящие межмодульные рёбра / все исходящие рёбра модуля; при отсутствии рёбер — `0` |
| Внутренняя связность модуля | внутренние рёбра / все рёбра с источником в модуле; хранится вместе с числителем и знаменателем, а не вместо них |
| Размер внешнего интерфейса модуля | число классов модуля, имеющих хотя бы одно входящее ребро из другого модуля |
| Циклические зависимости модулей | сильно связные компоненты графа межмодульных зависимостей размером больше одного модуля |
| Покрытие строк | покрытые строки / все исполняемые строки; рассчитывается из отчёта `Clover XML` для метода, класса, модуля и проекта; при отсутствии отчёта — `null` |
| Изменение показателя | текущее значение минус значение из базового отчёта для того же элемента |

Конструктор исключается из графа `LCOM4`: внедрение нескольких зависимостей через продвигаемые свойства иначе искусственно связывает все методы. Интерфейсы, абстрактные методы и классы с менее чем двумя учитываемыми методами получают `null`, а не фиктивный ноль. Вместе с числом нужно хранить количество учитываемых методов и точное название формулы: обозначение `LCOM` без уточнения неоднозначно.

### Стоимость и риски

Плюсы собственного сборщика:

- схема и семантика полей принадлежат проекту;
- собираются только нужные данные;
- нет плагина `Composer`, интерактивного подтверждения формул и преобразования чужой схемы;
- каждую формулу можно покрыть небольшими входными примерами и сравнить с ручным расчётом;
- один обход синтаксического дерева потенциально заметно экономнее полного `PhpCodeArcheology`.

Риски:

- нужно поддерживать новые конструкции `PHP` и правила подсчёта точек ветвления;
- сцепление методов требует корректно учитывать вызовы, свойства, трейты, наследование, статические методы и продвигаемые свойства;
- динамические вызовы, строки с именами классов, контейнеры зависимостей и рефлексия статически разрешаются не полностью;
- собственный форматтер опирается на программный контракт `Deptrac`; его совместимость нужно проверять при обновлении основной версии;
- собственная реализация без эталонных примеров создаёт ложное ощущение точности;
- предположение о выигрыше производительности нужно подтвердить тем же тройным прогоном на `TasK/Development`.

### Предварительный вывод

**Узкий собственный сборщик на `nikic/php-parser` вместе с `Deptrac` выглядит предпочтительнее как конечная архитектура, но пока не доказан прототипом.** `PhpCodeArcheology` следует оставить эталонным внешним источником до проверки.

Критерии переключения на собственную реализацию:

1. Формулы выше закреплены примерами с ручным ожидаемым результатом.
2. Все 3 592 файла `TasK/Development/src` разбираются без потерь.
3. Расхождения с `PhpCodeArcheology`, `PhpMetrics` и графом `Deptrac` объяснены формулами.
4. Три запуска измерены по той же методике; целевой отчёт существенно меньше 55,1 МБ, пиковая память — меньше 524 МиБ.
5. Объём поддержки ограничен сбором выбранных метрик; дашборд и правила качества не проникают в анализатор.

До такого прототипа зависимость `PhpCodeArcheology` удалять рано. После успешной проверки она становится только исследовательским эталоном и может быть исключена из постоянных зависимостей.

## Поиск проблемных мест

### Метрики и диагностики

Полный снимок метрик и поиск нарушений — разные контуры:

- метрика отвечает «сколько?» для каждого элемента и позволяет строить распределения, историю и комбинированные сигналы;
- диагностика отвечает «где нарушено правило?» и обычно выводит только элементы, пересёкшие порог;
- одна метрика не доказывает проблему: крупный класс может быть целостным, а небольшой класс — иметь несколько несвязанных обязанностей;
- для ИИ-агента полезны оба результата: исходные числа для проверки вывода и отдельный список кандидатов на изучение.

Собственный `report.json` должен поэтому иметь независимые блоки `metrics` и `findings`. Каждый элемент `findings` содержит стабильный идентификатор правила, объект, исходные значения и объяснение, но в первой версии не блокирует `CI`. Сначала используются относительное ранжирование и сочетания сигналов, например:

- метод одновременно входит в верхние 5 % по `LOC` и сложности;
- класс крупный, имеет несколько компонентов `LCOM4` и высокий максимум сложности метода;
- класс одновременно имеет много исходящих связей и часто изменяется;
- модуль имеет цикл или высокую долю исходящих межмодульных связей.

Абсолютные пороги можно добавить после просмотра распределений на нескольких проектах. Это не отменяет диагностические инструменты: они находят локальные запахи, которые не выражаются выбранной моделью метрик.

### `PHPMD` как диагностический инструмент

`PHPMD` вычисляет метрики, но штатно применяет их внутри пороговых правил. Он может находить:

- высокую цикломатическую и `NPath`-сложность;
- чрезмерную длину метода или класса;
- большое количество параметров, методов, публичных элементов и свойств;
- высокий `WMC` класса;
- большое число зависимостей `CBO`;
- большую глубину наследования и число потомков;
- неиспользуемые приватные элементы и отдельные запахи дизайна.

Его стандартный `XML`, `JSON`, `SARIF` и другие отчёты содержат только сработавшие правила. Элемент ниже порога отсутствует, поэтому отчёт не заменяет полный снимок `LOC`, `LCOM4`, `Ca/Ce` и графа модулей. Занижение всех порогов позволило бы извлекать часть чисел из текстов диагностик, но сделало бы формат шумным и зависимым от сообщений правил.

Вывод: **`PHPMD` пригоден как дополнительный детектор, но не нужен в первой версии цепочки**. Большинство полезных для эпика правил размера, сложности и связанности выводятся из собственного отчёта. Если после пилота останется конкретный пробел, стоит подключить отдельное правило, например `NPathComplexity`, а не полные наборы `codesize` и `design`.

### Сравнение диагностических альтернатив

| Инструмент | Что находит с помощью метрик | Полный снимок | Роль в предлагаемой цепочке |
|---|---|---|---|
| собственный сборщик и агрегатор | размер, сложность, `LCOM4`, `Ca/Ce`, циклы и комбинированные кандидаты | да, по выбранной схеме | основной источник и ранжирование проблемных мест |
| `PHPMD` | `CC`, `NPath`, `WMC`, длина, количество элементов, `CBO`, наследование и запахи | нет, только нарушения порогов | точечные правила после выявления пробела |
| `PHP_CodeSniffer` + `Slevomat` | цикломатическая и когнитивная сложность, уровень вложенности | нет, только нарушения; отдельные сниффы поддерживают информационные метрики | предпочтительный локальный контроль без новой зависимости |
| `PHPStan` | ошибки типов и потока данных, часть неиспользуемого приватного кода, пользовательские правила | не является сборщиком метрик | обязательный семантический контроль; уже работает на уровне `max` |
| `Deptrac` | запрещённые и непокрытые архитектурные зависимости | штатный `JSON` неполон; собственный форматтер даёт граф | архитектурные нарушения и вход для модульных метрик |
| `Phanalist` | `LCOM4`, fan-in/fan-out, сложность, плотность сложности и архитектурные правила | нет, только сработавшие правила | более близкая к модели альтернатива `PHPMD`, но дублирует сборщик и менее зрелая |
| `PHP Insights` | проблемы качества, сложности, архитектуры и стиля, четыре сводные оценки | нет полного набора сырых метрик | удобный аудит, но значительное пересечение с `PHPCS`; в прогоне 18 657 диагностик |
| `SonarQube` | цикломатическая и когнитивная сложность, дублирование, покрытие, запахи и история | да, внутри платформы | наиболее полный готовый комплекс, но требует отдельной инфраструктуры и выходит за границы локального пакета |

Текущий `ruleset.xml` включает только `PSR-12` и собственные сниффы пакета. При этом необходимые реализации уже установлены транзитивно и напрямую. Для отдельной задачи интеграции стоит проверить включение:

```xml
<rule ref="Generic.Metrics.CyclomaticComplexity"/>
<rule ref="Generic.Metrics.NestingLevel"/>
<rule ref="SlevomatCodingStandard.Complexity.Cognitive"/>
```

Пороговые значения нельзя добавлять скрыто как побочный результат исследования: они должны следовать модели метрик, иметь предупреждающий и блокирующий уровни и проверяться на `coding-standard` и `TasK/Development`.

### Рекомендуемое разделение ответственности

1. Собственный сборщик и агрегатор формируют полный снимок и неблокирующий список `findings`.
2. `PHP_CodeSniffer` и `Slevomat` дают быструю обратную связь по сложности и вложенности на строке кода.
3. `PHPStan` остаётся источником семантических ошибок и части мёртвого кода.
4. `Deptrac` контролирует разрешённость архитектурных зависимостей и отдаёт полный граф через собственный форматтер.
5. `PHPMD`, `Phanalist` и `PHP Insights` не добавляются одновременно: конкретный инструмент или правило подключается только для доказанного непокрытого сценария.
6. `SonarQube` имеет смысл пересматривать только при появлении требования к централизованной истории, анализу нескольких языков и серверному интерфейсу.

## Решение по внешнему инструменту

Среди готовых внешних инструментов основой выбран **`PhpCodeArcheology` 2.11.x**.

Главный критерий — полнота машинного отчёта уровня класса. `PhpCodeArcheology` единственный из проверенных кандидатов предоставляет в одном `JSON` все поля, необходимые запланированному агрегатору, включая количество свойств. Это уменьшает количество источников и собственных вычислений на следующем этапе.

`PhpMetrics` не оставлен как запасная зависимость: совпадение `LCOM` уже зафиксировано, а постоянная установка второго анализатора увеличила бы стоимость поддержки. Его можно временно подключать для повторной перекрёстной проверки формул.

`PDepend` не выбран из-за отсутствия `JSON` и `LCOM` в полученном отчёте. Для целевой модели потребовались бы преобразование `XML` и дополнительный источник метрик.

Расширенный поиск не изменил выбор основы:

- `PhpCodeArcheology` остаётся единственным проверенным инструментом с полным набором полей уровня класса в одном `JSON`;
- `scc` рекомендуется как дополнительный источник размера проекта и файлов, а не как конкурент анализатору уровня класса;
- `php-dep` заслуживает повторной оценки как источник графа зависимостей после стабильного релиза;
- `Phanalist` и `PHP Insights` полезны как диагностические анализаторы, но их отчёты ориентированы на нарушения;
- `PHPLOC`, `php-linter`, `PHP Stability Metrics` и `PHPMD` закрывают только отдельные части модели.

Проверка производительности также не изменила решение. `PhpMetrics` быстрее и экономнее по памяти, но не содержит количества свойств. Полный запуск `PhpCodeArcheology` на 3 592 файлах занимает около 22 секунд и 524 МиБ памяти: это заметная цена, но допустимая для локального и периодического запуска. Если метрики войдут в каждый запуск `CI`, частоту и лимит памяти нужно закрепить отдельно.

После рассмотрения собственной реализации решение стало двухэтапным:

1. `PhpCodeArcheology` остаётся выбранным внешним эталоном и текущей зависимостью.
2. Перед реализацией агрегатора нужен ограниченный прототип собственного сборщика на `nikic/php-parser`. Если он проходит критерии переключения, постоянной основой становится собственный сборщик вместе с графом `Deptrac`; иначе сохраняется `PhpCodeArcheology`.

Для поиска проблемных мест собственный отчёт дополняется неблокирующим блоком `findings`, а быстрые локальные ограничения реализуются уже доступными сниффами `PHP_CodeSniffer` и `Slevomat`. `PHPMD` не добавляется целиком: отдельное правило можно подключить позже только для подтверждённого пробела.

В `composer.json` закреплены:

```json
{
    "require-dev": {
        "php-code-archeology/php-code-archeology": "^2.11"
    },
    "config": {
        "allow-plugins": {
            "php-code-archeology/php-code-archeology": true
        }
    }
}
```

## Ограничения исследования и вопросы для следующих задач

- Предложенные формулы собственного сборщика ещё не реализованы и не проверены на эталонных примерах.
- Ненулевой `Ca` не проверен на выбранных пяти классах: `php-dep` также показал нулевое количество входящих зависимостей.
- Проверка `PHP` 8.4 покрывает используемые в пакете конструкции, атрибуты и `readonly`-классы, но не все возможности языка.
- Не исследована стабильность `JSON`-схемы между минорными версиями `PhpCodeArcheology`.
- Не определено, учитывать ли во внешней связанности встроенные типы и типы из зависимостей или только зависимости внутри проекта.
- Перед реализацией нужно закрепить определения обязательных метрик примерами с ручным ожидаемым результатом.
- Агрегатор должен читать только закреплённый набор полей и выдавать понятную ошибку при изменении схемы входного `JSON`.
- Поиск альтернатив не является исчерпывающим каталогом всех коммерческих и серверных платформ; приоритет отдавался локальным инструментам с открытым исходным кодом и машинным отчётом.
- Измеренное время зависит от оборудования, состояния кешей и версии проекта; числа подходят для относительного сравнения в указанной среде, а не как универсальная гарантия.
- Правила формирования `findings` и абсолютные пороги сложности ещё не проверены на распределениях нескольких проектов.

## Воспроизведение

Команды меняют `composer.json`; невыбранные зависимости после исследования удаляются.

```bash
mkdir -p var/metrics

composer require --dev phpmetrics/phpmetrics:^2.10
vendor/bin/phpmetrics --report-json=var/metrics/phpmetrics.json src

composer require --dev pdepend/pdepend:^2.16
vendor/bin/pdepend --summary-xml=var/metrics/pdepend.xml src

composer config allow-plugins.php-code-archeology/php-code-archeology true
composer require --dev php-code-archeology/php-code-archeology:^2.11
printf 'y\n' | vendor/bin/phpcodearcheology \
    --report-type=json \
    --report-dir=var/metrics/code-archeology \
    src

composer remove --dev phpmetrics/phpmetrics pdepend/pdepend
```

После первого подтверждения версии формул:

```bash
vendor/bin/phpcodearcheology \
    --report-type=json \
    --report-dir=var/metrics/code-archeology \
    src
```

Дополнительные инструменты запускались из изолированных временных каталогов, чтобы не менять зависимости пакета. Основной каталог теста и пример измерения времени:

```bash
TARGET="$HOME/MyProjects/TasK/Development/src"

/usr/bin/time -f '%e %M' -o /tmp/scc-src.time \
    scc -a --by-file -i php -f json "$TARGET" > /tmp/scc-src.json

phanalist --src "$TARGET" --output-format json > /tmp/phanalist-src.json
php-dep analyze "$TARGET" --format=json -q > /tmp/php-dep-src.json
phpinsights analyse "$TARGET" --format=json --no-interaction > /tmp/phpinsights-src.json
phploc --log-json /tmp/phploc-src.json "$TARGET"
```

Формат файла времени — секунды и максимальный резидентный размер в КиБ. Для таблицы каждую команду запускали три раза; аналогичная оболочка `/usr/bin/time` использовалась для всех инструментов.
