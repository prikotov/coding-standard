# TASK-feat-di-non-service-exclude-validator: Проверка исключений несервисных классов из Symfony DI

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- Конвенция требует исключать сообщения и объекты данных из автоматической регистрации Symfony DI, но пакет это не проверяет.
- Из-за выборочных исключений одни `Command`, `Query` и DTO становятся сервисами, а другие нет; ошибка обнаруживается только при ручном ревью конфигурации проекта-потребителя.

### Варианты или путь решения (Solution Sketch)
- Добавить проверку модульных `services.yaml`, которая требует общие суффиксные исключения для несервисных классов.
- Дополнить её статической проверкой, запрещающей внедрение таких объектов через конструкторы сервисов, либо обоснованно выбрать другой механизм с тем же проверяемым результатом.

### Ожидаемый результат (Expected Result)
- Проект-потребитель автоматически получает понятную ошибку, если регистрирует `Command`, `Query` или DTO как сервис либо использует их как DI-зависимости.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)
> **User Story:** Как разработчик проекта-потребителя, я хочу автоматически проверять исключение сообщений и объектов данных из Symfony DI, чтобы конфигурация модулей оставалась последовательной и контейнер содержал только реальные сервисы.

### Цель по SMART (Goal)
- В рамках одной задачи добавить в `prikotov/coding-standard` воспроизводимую проверку модульной Symfony-конфигурации и ошибочного DI-внедрения `*Command`, `*Query`, `*Dto`, покрыть положительные и отрицательные сценарии тестами и включить проверку в стандартный проверочный контур пакета.

## 2. Контекст и Границы (Context and Scope)

- **Где делаем:** проверочные инструменты пакета в `bin/` и/или `src/`, их тесты в `tests/`, правила в `docs/conventions/modules/configuration.md`, подключение через Composer scripts при необходимости.
- **Текущее поведение:** конвенция уже требует суффиксные `exclude`, но автоматической проверки конфигурации и DI-зависимостей нет.
- **Границы (Out of Scope):** массовое исправление проектов-потребителей, изменение Symfony DI, бизнес-кода или публичных CQRS-контрактов.

## 3. Требования, MoSCoW (Requirements)

### 🔴 Обязательно (Must Have)
- [ ] Проверять модули с автоматическим `resource`-импортом и требовать общие исключения для всех `*Command.php`, `*Query.php` и `*Dto.php`, независимо от их вложенного каталога.
- [ ] Не считать достаточным перечисление отдельных файлов или отдельных DTO-каталогов, если оно не покрывает весь модуль.
- [ ] Обнаруживать внедрение `Command`, `Query` и DTO в конструкторы сервисов либо документировать и реализовать эквивалентную проверку через скомпилированный Symfony-контейнер.
- [ ] Выдавать диагностическое сообщение с файлом конфигурации или местом ошибочной зависимости и рекомендуемым исправлением.
- [ ] Покрыть тестами корректные общие маски, выборочные исключения, отсутствие исключений и ошибочное DI-внедрение.
- [ ] Подключить проверку к стандартной команде пакета, предназначенной для проекта-потребителя.
- [ ] Обновить конвенцию и пользовательскую документацию запуска проверки.

### 🟡 Желательно (Should Have)
- [ ] Тем же механизмом поддержать обязательные несервисные суффиксы `*Event.php`, `*Exception.php`, `*Enum.php` и `*Vo.php`, уже перечисленные в конвенции.

### 🟢 Опционально (Could Have)
- [ ] Предложить машиночитаемый формат результата для CI.

### ⚫ Не будем делать (Won't Have)
- [ ] Автоматически переписывать `services.yaml` проекта-потребителя.
- [ ] Запрещать Symfony console `Command`, которые являются Presentation-сервисами и должны регистрироваться в контейнере.
- [ ] Требовать один буквальный вариант YAML-маски, если другая форма обеспечивает эквивалентное полное покрытие.
- [ ] Добавлять Symfony как обязательную runtime-зависимость пакета без отдельного обоснования совместимости.

## 4. План реализации (Implementation Plan)

1. [ ] Исследовать текущие команды проверки пакета и выбрать минимальную точку интеграции для анализа проекта-потребителя.
2. [ ] Формализовать отличие Application `Command`/`Query` от Symfony console `Command` и правила полного покрытия `exclude`.
3. [ ] Реализовать проверку конфигурации и ошибочных DI-зависимостей с понятной диагностикой.
4. [ ] Добавить изолированные положительные и отрицательные фикстуры, включая контекстные DTO рядом с use case и domain service.
5. [ ] Обновить документацию и включить проверку в `composer check` пакета.

## 5. Критерии приёмки (Definition of Done)

- [ ] Выборочные исключения отдельных сообщений или DTO отклоняются проверкой.
- [ ] Общие исключения всех Application `Command`, Application `Query` и DTO принимаются.
- [ ] Ошибочное внедрение несервисного объекта в сервис обнаруживается автоматически.
- [ ] Symfony console `Command` не даёт ложного срабатывания.
- [ ] Тесты подтверждают запуск из корня изолированного проекта-потребителя.
- [ ] `composer check` проходит без ошибок.
- [ ] Документация описывает назначение, ограничения и способ запуска проверки.

## 7. Риски и зависимости (Risks and Dependencies)

- YAML допускает несколько эквивалентных форм ресурсов и исключений; проверка не должна сравнивать конфигурацию только как текст.
- Постфикс `Command` используется также Symfony console-командами, поэтому правило обязано учитывать слой и путь.
- Проверка скомпилированного контейнера может потребовать необязательной интеграции с Symfony; предпочтителен механизм без новой обязательной зависимости.
