# TASK-feat-shared-dto-reuse-validator: Проверка общих DTO модуля на переиспользование в нескольких use case'ах

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- Общий пул DTO модуля `Module\{ModuleName}\Application\Dto\` предназначен для **переиспользуемых** DTO — проекций доменных сущностей (`Model → DTO`), которые возвращаются из нескольких use case'ов.
- На практике злоупотребляют исключением: кладут туда DTO, который по сути use-case-специфичный (используется одним query/command), хотя должен лежать рядом с владельцем в `UseCase\{Case}\`.
- Вручную отличить «реально общий» DTO от «случайно в общем пуле» сложно — нужен анализ фактического использования по коду.
- Разработка ведётся AI-агентами; агент может не прочитать конвенцию → текст-doc не барьер. Нужна **автоматическая валидация**.

### Варианты или путь решения (Solution Sketch)
- CLI-анализатор (`bin/validate-dto-usage`, opt-in — по аналогии с `validate-md-links`, `validate-language`).
- Для каждого DTO из `Module\{M}\Application\Dto\` считает количество use case'ов (query/command-handler'ов), в return-типе которых встречается этот DTO.
- Если DTO используется ≤ порога (по умолчанию 1) — это сигнал, что ему место рядом с владельцем, а не в общем пуле.
- Проверка **не привязана к имени DTO** (суффиксу/префиксу) — только к фактическому переиспользованию. Не обходится переименованием.

### Ожидаемый результат (Expected Result)
- Команда находит DTO в `Module\{M}\Application\Dto\`, используемые ≤ порога use case'ами, и предлагает перенести их рядом с владельцем.
- Ручной разбор «общих» DTO на ревью перестаёт быть основным барьером — автоматика подсвечивает подозрительные.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)
> Как сопровождающий модуля, я хочу видеть общие DTO, которые по факту используются одним use case'ом, чтобы не плодить use-case-специфичные DTO в общем пуле и держать их рядом с владельцем.

### Goal (Цель по SMART)
- **S:** CLI `bin/validate-dto-usage` считает для каждого DTO из `Module\{M}\Application\Dto\` количество query/command-handler'ов, в return-типе которых встречается DTO.
- **M:** DTO с числом использований ≤ порога (по умолчанию 1) помечаются warning; тесты покрывают случаи 0/1/N использований и игнор корневого пула.
- **A:** Локальный per-module анализ (grep/regex по `UseCase\{Query,Command}\` одного модуля); кеш списка файлов use case'ов на модуль; без глобального графа.
- **R:** Предотвращает злоупотребление общим пулом DTO, держит DTO рядом с владельцем; валидация не зависит от имени (не обходится переименованием).
- **T:** Одна задача, C3.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** `src/DtoUsage/` (логика + DTO) + `bin/validate-dto-usage` (thin CLI).
- **Текущее поведение:** `DtoStructureSniff` проверяет структуру DTO и запрещает `Domain\Dto\`. Переиспользование общих DTO не анализируется.
- **Границы (Out of Scope):**
  - Корневой `Common\Application\Dto\` (общие DTO приложения — `PaginationDto`, `IdDto`, `SortDto`) не проверяем — он заведомо общий. Проверяем только `Module\{M}\Application\Dto\`.
  - Глобальный граф зависимостей не строим — только локальный per-module анализ return-типов.
  - Автоматическое перемещение DTO не делаем — только диагностика.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)
- [ ] CLI `bin/validate-dto-usage`: для каждого DTO из `Module\{M}\Application\Dto\` считает количество query/command-handler'ов в `Module\{M}\Application\UseCase\{Query,Command}\`, в return-типе которых встречается DTO (учитывая `: <Dto>`, `: ?<Dto>`, `@return ...<Dto>`, `\FQCN\Dto`).
- [ ] DTO с числом использований ≤ порога помечаются warning с предложением перенести рядом с владельцем и ссылкой на `dto.md`.
- [ ] Порог настраивается (по умолчанию 1) — через `.coding-standard.php` (ключ `dto_usage.min_uses`).
- [ ] Корневой `Common\Application\Dto\` не проверяется.
- [ ] Список файлов `UseCase\` кешируется на модуль (производительность).
- [ ] PHPUnit-тесты: 0, 1, 2+ использований DTO; корректное игнорирование корневого пула; FQCN-форма return-типа.

### 🟡 Should Have (Желательно)
- [ ] Поддержка DTO как поля другого DTO / параметра (не только return-тип handler'а) — расширенный учёт использования.
- [ ] Конфиг: исключения (allowlist общих DTO), свои пороги.

### ⚫ Won't Have (Не будем делать)
- [ ] Глобальный граф зависимостей DTO.
- [ ] Автоматический рефакторинг (перемещение файлов).
- [ ] Проверка по имени DTO (суффиксу) — намеренно от названия не зависит.
- [ ] Встраивание LSP-сервера или PHPStan-collector в пакет — держим пакет лёгким.

## 4. Implementation Plan (План реализации)
*Заполняется исполнителем перед стартом.*
- Сканирование `src/` (или `paths` из конфига) → список DTO в `Module\{M}\Application\Dto\` (по namespace/path).
- Список query/command-handler'ов в `Module\{M}\Application\UseCase\{Query,Command}\` (кеш на модуль).
- Для каждого handler'а извлечь return-тип `__invoke()`/метода (regex или轻кий токенайзер), сопоставить с DTO.
- Подсчёт: DTO → множество handler'ов; len ≤ порога → warning.
- Thin CLI: читает `.coding-standard.php` (`dto_usage`), печатает отчёт, exit code (0 по умолчанию, 1 в `--strict`).

## 5. Definition of Done (Критерии приёмки)
- [ ] DTO из `Module\{M}\Application\Dto\`, используемые ≤ порога use case'ами, помечаются.
- [ ] Корневой `Common\Application\Dto\` не проверяется.
- [ ] Не зависит от имени DTO (только переиспользование).
- [ ] Производительность приемлема (кеш файлов use case'ов).
- [ ] `composer check` пройден, PHPUnit-тесты покрывают ключевые сценарии.

## 7. Risks and Dependencies (Риски и зависимости)
- Cross-file анализ требует обхода файловой системы (не per-file sniff) — отсюда выбор формы: отдельный CLI-анализатор, а не sniff.
- DTO может использоваться не в return-типе, а как поле другого DTO / параметр — эвристика по return-типу может пропускать; для начала достаточно return-типов (Should Have — расширить).
- Ложные срабатывания на DTO, возвращаемых одним query, но легитимно общих (планируют переиспользовать) — сглаживается allowlist'ом в конфиге.
- Регекс по return-типу хрупок (FQCN, union/intersection types, PHPDoc) — учитывать основные формы; для сложных случаев рассмотреть лёгкий токенайзер вместо регекса.

## 9. Comments (Комментарии)
- **Эволюция подхода.** Задача прошла несколько итераций проектирования:
  1. Исходно — cross-file анализатор reused DTO (C3).
  2. Рассмотрена имя-эвристика (per-file sniff на суффикс `Request/Result/Response`, C1) — **отвергнута**: суффикс это симптом, обходится переименованием, не ловит суть (переиспользование).
  3. Рассмотрены `@shared`-маркер, PHPStan-collector, LSP-сервер — отвергнуты: меняют конвенцию / тяжёлая инфра / coupling.
  4. Возврат к cross-file CLI-анализатору — единственная валидация, не зависящая от имени и от того, прочитал ли агент конвенцию.
- **Контекст AI-агентов:** разработка ведётся агентами; агент может не прочитать doc → текст-инструкция не барьер, автоматика = основной. LSP у агентов есть, но не как замена CI-валидации.
