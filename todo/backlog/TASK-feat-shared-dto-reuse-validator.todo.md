# TASK-feat-shared-dto-reuse-validator: Проверка общих DTO модуля на переиспользование в нескольких use case'ах

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- Общий пул DTO модуля `Module\{ModuleName}\Application\Dto\` предназначен для **переиспользуемых** DTO — проекций доменных сущностей (`Model → DTO`), которые возвращаются из нескольких use case'ов.
- На практике агенты злоупотребляют исключением и кладут туда DTO, который по сути use-case-специфичный (используется одним query/command), хотя должен лежать рядом с владельцем в `UseCase\{Case}\`.
- Вручную отличить «реально общий» DTO от «случайно в общем пуле» сложно — нужен анализ фактического использования по коду.

### Варианты или путь решения (Solution Sketch)
- Анализатор (CLI-команда или sniff), который для каждого DTO из `Module\{M}\Application\Dto\` проверяет, в скольких use case'ах он используется в return-типе.
- Проверка локальная и лёгкая: для конкретного DTO достаточно погрепнуть `Module\{M}\Application\UseCase\Query\` (read-side, где return-типы) на маску этого DTO. Глобальный граф зависимостей строить не нужно.
- Если DTO используется в ≤ 1 query — это сигнал, что ему место рядом с владельцем, а не в общем пуле.

### Ожидаемый результат (Expected Result)
- Команда находит DTO в `Module\{M}\Application\Dto\`, используемые ≤ чем в 2 query-handler'ах, и предлагает перенести их рядом с владельцем.
- Ручной разбор «общих» DTO на ревью перестаёт быть основным барьером — автоматика подсвечивает подозрительные.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)
> Как сопровождающий модуля, я хочу видеть общие DTO, которые по факту используются одним use case'ом, чтобы не плодить DTO в общем пуле и держать их рядом с владельцем.

### Goal (Цель по SMART)
- **S:** Реализовать проверку переиспользования DTO из `Module\{M}\Application\Dto\` — считать use case'ы (query-handler'ы), в return-типе которых встречается DTO.
- **M:** DTO с числом использований ≤ порога (по умолчанию 1) помечаются как подозрительные; тесты покрывают случаи 0/1/N использований.
- **A:** Проверка локальная (grep по `UseCase\Query\` одного модуля), без глобального графа; кеш списка файлов use case'ов на модуль.
- **R:** Предотвращает злоупотребление общим пулом DTO, держит DTO рядом с владельцем.
- **T:** Одна задача, ограниченный scope.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** `src/` (новый analyzer в `src/` или расширение `DtoStructureSniff`) + `bin/` (CLI-entrypoint, если отдельная команда).
- **Текущее поведение:** `DtoStructureSniff` проверяет структуру DTO и запрещает `Domain\Dto\`. Переиспользование общих DTO не анализируется.
- **Границы (Out of Scope):**
  - Корневой `Application\Dto\` (общие DTO приложения — `PaginationDto`, `IdDto`, `SortDto`) не проверяем — он заведомо общий.
  - Глобальный граф зависимостей не строим — только локальный grep `UseCase\Query\` по модулю.
  - Автоматическое перемещение DTO не делаем — только диагностика.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)
- [ ] Для DTO из `Module\{M}\Application\Dto\` считается количество query-handler'ов в `Module\{M}\Application\UseCase\Query\`, в return-типе которых встречается этот DTO (учитывая `: <Dto>`, `: ?<Dto>`, `@return ...<Dto>`).
- [ ] DTO с числом использований ≤ порога помечаются (warning) с предложением перенести рядом с владельцем и ссылкой на `dto.md`.
- [ ] Порог настраивается (по умолчанию 1).
- [ ] Список файлов `UseCase\Query\` кешируется на модуль (производительность).
- [ ] Тесты на 0, 1, 2+ использований DTO; на корректное игнорирование корневого `Application\Dto\`.

### 🟡 Should Have (Желательно)
- [ ] Поддержка command-handler'ов (`UseCase\Command\`) — DTO как параметр/return command'ы.
- [ ] Конфиг проекта: свои пороги, исключения (allowlist общих DTO).

### ⚫ Won't Have (Не будем делать)
- [ ] Глобальный граф зависимостей DTO.
- [ ] Автоматический рефакторинг (перемещение файлов).
- [ ] Проверка DTO вне `Module\{M}\Application\Dto\`.

- [ ] Производительность приемлема (кеш файлов use case'ов).

## 7. Risks and Dependencies (Риски и зависимости)
- Cross-file анализ выходит за рамки классического per-file sniff'а — решение «sniff с FS-grep vs отдельный analyzer» принять на старте.
- DTO может использоваться не в return-типе, а как поле другого DTO / параметр — эвристика по return-типу может пропускать; для начала достаточно return-типов.
- Ложные срабатывания на DTO, которые возвращаются из одного query, но легитимно общие (например, планируют переиспользовать) — сглаживается allowlist'ом в конфиге.

## 8. Sources (Источники)

- Замечено в `prikotov/TasK`: 2 DTO в `Module\...\Application\Dto\` с use-case-суффиксами (`InitializeRegistrationResultDto`, `SessionLifecycleResultDto`), используемые одним query.

## 9. Comments (Комментарии)
- Решение «sniff vs analyzer» — открытое; sniff привлекательнее нулевой новой инфраструктурой, analyzer — концептуально чище для cross-file анализа (консистентно с `validate-md-links`).
- Эта задача выделена из первоначальной `TASK-sniff-dto-path-validation`, где strict-whitelist оказался неприменим (даёт ложные срабатывания на легитимные `Application\Service\`, `Application\Event\`, `Infrastructure\Service\`, `Integration\Dto\`).
