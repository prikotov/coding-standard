# TASK-metrics-tracked-snapshot: актуальный снимок метрик в Git

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

- `var/metrics/` является временным каталогом и исключается из Git, поэтому у проекта нет зафиксированного состояния метрик.
- Без снимка в базовой ветке PR вынужден заново анализировать две ревизии и не показывает обычный Git diff метрик.
- Отчёт содержит время запуска и commit, поэтому его нельзя хранить как стабильный lock-файл без постоянного шума и самоссылки.

### Варианты или путь решения (Solution Sketch)

- Добавить один полный канонический `coding-standard-metrics.lock.json` в корне проекта-потребителя.
- Хранить lock-файл в Git наравне с `composer.lock` и обновлять вместе с изменениями исходников, тестов или конфигурации анализа.
- Оставить промежуточные отчёты и HTML-дашборд в игнорируемом `var/metrics/`.
- Добавить режимы обновления и проверки актуальности lock-файла.

### Ожидаемый результат (Expected Result)

- В каждой ревизии проекта есть полный снимок метрик, соответствующий её исходникам и конфигурации.
- Обычный Git diff показывает, какие метрики изменил PR.
- CI отклоняет устаревший или вручную отредактированный lock-файл.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)

> Как ИИ-агент, проводящий код-ревью, я хочу всегда иметь актуальный снимок метрик в Git, чтобы сравнивать текущие правки с состоянием целевой ветки без повторного восстановления прошлого окружения.

### Goal (Цель по SMART)

Добавить детерминированный `coding-standard-metrics.lock.json`, содержащий все метрики проекта-потребителя. Команда обновления должна формировать его из текущих исходников, тестов и конфигурации, а команда проверки — завершаться ошибкой при любом расхождении. Проверка: lock-файл, созданный до коммита из подготовленных изменений, совпадает с результатом на чистом HEAD после коммита; повторный запуск не меняет файл.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** схема полного снимка, агрегатор, публичный CLI, конфигурация проекта-потребителя, README и тесты.
- **Отслеживаемый артефакт:** `coding-standard-metrics.lock.json` в корне проекта.
- **Временные артефакты:** `var/metrics/`, включая зеркальные JSON и HTML-дашборд, остаётся в `.gitignore`.
- **Границы (Out of Scope):**
  - Не коммитим HTML и промежуточные файлы анализаторов.
  - Не храним несколько исторических снимков внутри текущей ревизии.
  - Не включаем время генерации, абсолютные пути и commit текущего lock-файла в канонический снимок.
  - Не допускаем ручного редактирования lock-файла.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)

- [ ] Lock-файл содержит полную модель проекта: project-, module-, class- и method-level метрики, findings, версии схемы и определений.
- [ ] Lock-файл является самодостаточным: сравнение не требует зеркальных файлов из `var/metrics/`.
- [ ] Ключи и коллекции сортируются детерминированно; относительные пути нормализуются.
- [ ] Из lock-файла исключаются `generated_at`, абсолютные пути и commit hash, создающий самоссылку.
- [ ] Метаданные содержат версии измерителей, отпечаток конфигурации и отпечаток анализируемых входов без самого lock-файла.
- [ ] Git-derived метрики учитывают подготовленные и рабочие изменения как одну будущую ревизию, чтобы снимок до коммита совпадал со снимком чистого HEAD после коммита.
- [ ] Публичная команда умеет обновить lock-файл и проверить его актуальность без записи.
- [ ] Режим проверки возвращает ненулевой код и краткий diff причин, если исходники, тесты, конфигурация или ожидаемые метрики изменились.
- [ ] README требует коммитить lock-файл и обновлять его в каждом PR, затрагивающем входы анализа.
- [ ] Шаблон `.gitignore` исключает `var/metrics/`, но не исключает `coding-standard-metrics.lock.json`.
- [ ] Автоматические тесты проверяют повторяемость, ручную правку, изменение входа и стабильность до/после коммита.

### 🟡 Should Have (Желательно)

- [ ] `composer metrics` обновляет lock-файл и затем строит временный HTML-дашборд из того же снимка.
- [ ] Отдельный режим быстро проверяет отпечаток входов до дорогого полного пересчёта.

### ⚫ Won't Have (Не будем делать)

- [ ] Не используем `var/metrics/report.json` как отслеживаемый файл.
- [ ] Не добавляем дату генерации ради «истории» — историю предоставляет Git.
- [ ] Не коммитим `comparison.json`, `summary.md` и HTML: они выводятся из двух версий lock-файла для конкретного PR.

## 4. Implementation Plan (План реализации)

1. [ ] Зафиксировать каноническую схему полного lock-файла и состав входного отпечатка.
2. [ ] Научить агрегатор формировать один полный снимок без изменчивых метаданных.
3. [ ] Реализовать режимы `update` и `check` публичной команды.
4. [ ] Стабилизировать Git-derived метрики для подготовленного состояния и чистого HEAD.
5. [ ] Обновить конфигурацию, README, потребительские тесты и проверить сценарий на TasK.

## 5. Definition of Done (Критерии приёмки)

- [ ] Новый проект получает документированное правило коммитить `coding-standard-metrics.lock.json`.
- [ ] После изменения кода обновление lock-файла создаёт осмысленный Git diff метрик.
- [ ] На чистом checkout режим проверки подтверждает актуальность lock-файла без изменений рабочей копии.
- [ ] Временный `var/metrics/` остаётся исключённым из Git.
- [ ] `composer check` зелёный.

## 6. Verification (Самопроверка)

```bash
vendor/bin/coding-standard-metrics --update-lock
git diff -- coding-standard-metrics.lock.json
vendor/bin/coding-standard-metrics --check-lock
composer check
```

## 7. Risks and Dependencies (Риски и зависимости)

- Полный снимок TasK может быть крупным; один канонический JSON должен оставаться пригодным для Git diff и сжатия.
- Массовое изменение схемы или конфигурации даст большой diff; такой переход оформляется отдельно от изменений production-кода.
- Churn зависит от истории Git; алгоритм подготовленного состояния должен исключить расхождение до и после создания коммита.
- Покрытие должно собираться воспроизводимо в одинаковом окружении; нестабильные тесты делают lock-файл нестабильным.

## 8. Sources (Источники)

- `var/metrics/report.json` — текущий временный снимок.
- `composer.lock` — пример отслеживаемого воспроизводимого состояния проекта.
- `TASK-metrics-composer-integration` — сбор метрик проекта-потребителя.

## 9. Comments (Комментарии)

- Git хранит историю lock-файла, поэтому отдельная БД истории для сравнения соседних ревизий не нужна.
- `comparison.json` и `summary.md` остаются полезными производными: они интерпретируют raw diff двух lock-файлов для ИИ-агента и человека.
