# TASK-metrics-pr-review-workflow: изменение метрик как артефакт код-ревью

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

- Даже отслеживаемая структура метрик бесполезна, если CI не проверяет её актуальность и не превращает Git diff отчётов в понятный результат ревью.
- ИИ-агенту не задано, когда запускать метрики, какой commit считать базой и как реагировать на ухудшение.
- Результат анализа теряется после CI и не является частью материалов код-ревью.

### Варианты или путь решения (Solution Sketch)

- Извлекать `baseline` как дерево `.coding-standard/metrics/` на merge-base с целевой веткой, а `current` брать из проверяемого PR.
- Проверять, что текущая JSON-структура заново получается из HEAD без изменений.
- Передавать две версии структуры в команду сравнения и сохранять их вместе с `comparison.json` и `summary.md` одним артефактом PR.
- Добавить инструкцию ИИ-агенту: изучить дельту до одобрения и потребовать исправление либо явное обоснование регрессии в изменённой области.

### Ожидаемый результат (Expected Result)

- Каждый PR может предоставить воспроизводимое изменение метрик относительно своей целевой ветки.
- Raw diff `.coding-standard/metrics/**/*.json` остаётся частью самого PR и доступен без скачивания CI-артефакта.
- ИИ-агент использует дельту как обязательный вход код-ревью наряду с diff кода и конвенциями.
- Кодовая база получает направленность на улучшение: необъяснённые регрессии не проходят ревью незаметно.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)

> Когда ИИ-агент проверяет PR, я хочу приложить изменение метрик между merge-base и HEAD, чтобы решение о ревью учитывало измеренное направление изменения качества.

### Goal (Цель по SMART)

Добавить документированный потребительский сценарий и CI-пример, которые проверяют актуальность текущей структуры, извлекают её базовую версию из merge-base, запускают детерминированное сравнение и публикуют единый артефакт PR. Инструкция ИИ-агента должна требовать анализа регрессий в изменённой области до одобрения. Проверка: сценарий выполняется на тестовом PR TasK и повторно создаёт одинаковую дельту для тех же commit и деревьев отчётов.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** публичный CLI-оркестратор или скрипт пакета, пример CI, README и копируемая конвенция для ИИ-агентов.
- **Базовая ревизия:** дерево отслеживаемых JSON из `.coding-standard/metrics/` на merge-base текущего HEAD и целевой ветки PR.
- **Текущая ревизия:** отслеживаемая структура проверяемого PR; для локального режима допускаются обновлённые незакоммиченные отчёты.
- **Границы (Out of Scope):**
  - Не храним долговременную историю в БД.
  - Не публикуем HTML-дашборд как обязательный артефакт ревью.
  - Не одобряем PR автоматически только по отсутствию регрессий метрик.
  - Не скрываем несовместимость снимков под пустым сравнением.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)

- [x] Сценарий явно определяет target branch, merge-base и HEAD, сохраняет commit каждого снимка.
- [x] До сравнения режим `--check-snapshot` подтверждает, что текущая структура соответствует HEAD и не меняет рабочую копию.
- [x] Baseline рекурсивно извлекается из Git на merge-base с сохранением зеркала путей, current читается из PR; повторный запуск анализаторов для базовой ревизии не требуется.
- [x] Совместимость схемы, конфигурации и версий измерителей проверяется по метаданным корневых отчётов; несовместимость блокирует сравнение.
- [x] В сравнение передаётся список файлов текущего Git diff для выделения изменённой области.
- [x] Артефакт PR содержит `baseline/.coding-standard/metrics/`, `current/.coding-standard/metrics/`, `comparison.json`, `summary.md` и метаданные воспроизведения.
- [x] `summary.md` публикуется в доступном для ревью виде; полный JSON остаётся доступен ИИ-агенту.
- [x] Копируемая инструкция требует от ИИ-агента прочитать `comparison.json`, связать регрессии с diff кода и отразить вывод в ревью.
- [x] Необъяснённая регрессия в изменённой области является причиной не одобрять ревью; допустимое ухудшение должно быть явно обосновано в PR.
- [x] Улучшения и устранённые циклы фиксируются в резюме, чтобы агент видел положительный вектор.
- [x] Сценарий протестирован на PR или паре commit проекта TasK.

### 🟡 Should Have (Желательно)

- [x] Добавлен пример GitHub Actions с публикацией каталога через artifact и Markdown через job summary.
- [x] Локальный режим извлекает структуру из Git как baseline и использует обновлённую рабочую структуру как current без checkout исходников базовой ревизии.

### ⚫ Won't Have (Не будем делать)

- [ ] Не вводим единый универсальный порог качества для всех проектов.
- [ ] Не считаем отсутствие регрессии достаточным условием одобрения PR.
- [ ] Не требуем HTML-дашборд для машинного код-ревью.

## 7. Risks and Dependencies (Риски и зависимости)

- На старой базовой ветке структура метрик может отсутствовать; первый PR внедрения фиксирует исходную линию без сравнения.
- Изменение конфигурации анализа или версии метрики может сделать снимки несовместимыми; миграция структуры оформляется отдельно от изменения production-кода.
- Покрытие и тестовая статистика зависят от одинакового окружения и набора тестов в обеих ревизиях.
- Для fork PR публикация комментария может быть ограничена правами; artifact и job summary должны работать без write-доступа.
