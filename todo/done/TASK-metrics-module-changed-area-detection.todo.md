# TASK-metrics-module-changed-area-detection: корректно определять изменённую область для модульных метрик

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- Отчёт ревью правильно замечает изменения отдельных файлов и классов, но может не признать затронутым модуль, в котором они находятся.
- Из-за этого ухудшение агрегированных показателей модуля не попадает в краткий раздел «Регрессии в изменённой области» и может остаться незамеченным при просмотре только `summary.md`.

### Варианты или путь решения (Solution Sketch)
- Определять принадлежность изменённой области модуля не по единственному `source_path`, а по путям входящих в модуль объектов.
- Сохранить в снимке достаточную информацию о составе модуля либо вычислять её при сравнении из классов текущего и базового снимков.

### Ожидаемый результат (Expected Result)
- Модульные регрессии автоматически попадают в краткое резюме, если PR изменяет хотя бы один файл соответствующего модуля.
- Ревьюверу не требуется вручную искать пропущенные модульные показатели в `comparison.json`.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)
> Как ревьювер, я хочу, чтобы агрегированные метрики затронутых модулей автоматически помечались как изменённая область, чтобы не пропустить модульную регрессию в кратком отчёте PR.

### Цель по SMART (Goal)
- Исправить формирование или сравнение снимков метрик так, чтобы `changed_area=true` выставлялся добавленному, изменённому или удалённому модулю при наличии изменённого файла этого модуля. Подтвердить поведение автоматическими тестами пакета и сценарием проекта-потребителя в рамках одного PR.

## 2. Контекст и Границы (Context and Scope)

- **Где делаем:** `src/Metrics/MetricsReportWriter.php`, `src/Metrics/MetricsComparison.php`, `src/Metrics/MetricsComparisonWriter.php`, связанные тесты в `tests/Metrics/`; точный минимальный вариант выбирает исполнитель.
- **Текущее поведение:** `MetricsReportWriter` записывает для module scope (области модуля) `source_path` из `$module['path']`, но агрегированные записи модулей могут не содержать `path`. Тогда снимок получает `source_path: ""`, а `MetricsComparison::changedArea()` не связывает модуль с относительными путями из `changed_paths` и возвращает `false`.
- **Воспроизведение:** в PR `prikotov/stocks2#198` новые и изменённые файлы/классы `TInvest` получили `changed_area=true`, а добавленный `Console:TInvest` и изменённый `Common:TInvest` — `source_path=""` и `changed_area=false`.
- **Границы (Out of Scope):** не менять направления улучшения/регрессии отдельных метрик, пороги качества и формат хранения исходных анализаторов; не исправлять метрики конкретного проекта-потребителя вручную.

## 3. Требования, MoSCoW (Requirements)

### 🔴 Обязательно (Must Have)
- [x] При изменении файла, принадлежащего модулю, соответствующее изменение module scope получает `changed_area=true`, даже если у агрегата нет единственного `source_path`.
- [x] При изменении файла другого модуля незатронутый модуль не получает ложный `changed_area=true`.
- [x] Поведение корректно для добавленных, изменённых и удалённых модулей с использованием состава current/baseline snapshot (текущего/базового снимка).
- [x] Модульная регрессия с `changed_area=true` попадает в раздел регрессий изменённой области `summary.md`.
- [x] Формат снимка остаётся детерминированным; если меняется его схема или атрибуты, совместимость версий обрабатывается явно.
- [x] Добавлен автоматический сценарий проекта-потребителя, где изменён файл модуля и проверены `comparison.json` и `summary.md`.

### 🟡 Желательно (Should Have)
- [x] Для модулей, распределённых по нескольким каталогам, принадлежность определяется по всем входящим объектам, а не по угаданному общему префиксу.
- [x] В `comparison.json` сохраняется достаточно данных, чтобы объяснить, почему модуль признан частью изменённой области.

### 🟢 Опционально (Could Have)
- [ ] Добавить диагностическое сообщение для модуля без объектов и без определяемого пути.

### ⚫ Не будем делать (Won't Have)
- [ ] Не считать все модули затронутыми при любом изменении проекта.
- [ ] Не подставлять путь модуля по соглашениям конкретного потребителя (`src/Module`, `apps/*` и т.п.).
- [ ] Не менять оценку направления метрик и не вводить новые блокирующие пороги.
- [ ] Не выполнять сопутствующий рефакторинг всего пайплайна метрик.

## 7. Риски и зависимости (Risks and Dependencies)

- Модуль может включать файлы из нескольких корней, поэтому один вычисленный префикс способен дать ложноотрицательный результат.
- Для удалённого модуля принадлежность нужно восстанавливать из baseline snapshot, а не только из current snapshot.
- Изменение структуры снимка может потребовать повышения версии схемы и явной обработки несовместимости старых артефактов.
