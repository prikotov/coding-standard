# TASK-feat-language-anglicism-ratio-validator: Проверка коэффициента англицизмов в документации

## 0. Простое описание (Human Brief)
### Проблема простыми словами (Problem)
- Русскоязычные проекты требуют человекочитаемые тексты на русском языке.
- Сейчас англоязычные фразы в задачах и документации обнаруживаются только ручным чтением PR.
- Из-за этого в `todo` и `docs` легко попадают фразы вроде `persisted rows` или `read-only facts`, хотя технические термины допустимы только как исключение.

### Варианты или путь решения (Solution Sketch)
- Добавить в `coding-standard` проверку коэффициента англицизмов для Markdown/text файлов.
- Исключать кодовые блоки, inline code (фрагменты в обратных кавычках), URL, пути, имена классов и разрешённые технические термины.
- На первом этапе показывать warning (предупреждение), чтобы внедрять проверку без резкого падения CI.

### Ожидаемый результат (Expected Result)
- Проекты-потребители смогут подключить проверку и заранее видеть файлы с подозрительно высокой долей англоязычных фраз.
- Ручной language review (языковое ревью) станет не обязательным основным барьером, а дополнительной страховкой.

## 1. Concept and Goal (Концепция и Цель)
### Story (User Story)
> Как сопровождающий русскоязычных проектов, я хочу автоматически видеть файлы с высоким коэффициентом англицизмов, чтобы не допускать англоязычные фразы в человекочитаемую документацию и задачи.

### Goal (Цель по SMART)
Добавить в `prikotov/coding-standard` CLI-команду (консольную команду) для расчёта коэффициента англицизмов в Markdown/text файлах. Команда должна находить файлы, где доля латинских слов в человекочитаемом тексте выше заданного порога, и показывать предупреждение с примерами подозрительных слов/фраз.

## 2. Context and Scope (Контекст и Границы)
* **Где делаем:**
  * `bin/` — CLI entrypoint (точка входа консольной команды), например `validate-language` или `validate-language.php`.
  * `src/` — сервисы анализа текста и Markdown.
  * `tests/` — unit-тесты для расчёта коэффициента и исключений.
  * `README.md` или `docs/` — инструкция подключения проверки в проекте-потребителе.
* **Текущее поведение:**
  * `coding-standard` проверяет стиль PHP и документационные конвенции, но не оценивает долю англоязычных фраз в Markdown/text файлах.
  * Ошибки языка сейчас ловятся только ручным чтением PR.
* **Границы (Out of Scope):**
  * Не переписывать текст автоматически.
  * Не запрещать все английские технические термины.
  * Не подключать проверку во все проекты-потребители в рамках этой задачи.
  * Не делать сложную лингвистику: на первом этапе достаточно эвристики и понятного отчёта.

## 3. Requirements (Требования, MoSCoW)
### 🔴 Must Have (Обязательно)
- [ ] Реализована CLI-команда для проверки Markdown/text файлов.
- [ ] Команда считает метрику `anglicism_ratio = latin_human_words / all_human_words`.
- [ ] Из расчёта исключаются code blocks (многострочные блоки кода), inline code (фрагменты в обратных кавычках), URL, пути файлов, namespaces (пространства имён), class/method names (имена классов/методов), task/epic IDs и PR/issue refs.
- [ ] Есть allowlist (белый список) технических терминов: например `Symfony`, `Doctrine`, `DTO`, `Command`, `Query`, `T-Invest`, `MOEX`, `API`, `CRUD`, `PR`.
- [ ] Команда выводит путь файла, коэффициент, превышенный threshold (порог) и примеры подозрительных слов/фраз.
- [ ] На первом этапе режим по умолчанию — warning (предупреждение), без жёсткого падения проверки.
- [ ] Есть тесты на русский текст, смешанный текст, code blocks, inline code, URL, пути и allowlist.

### 🟡 Should Have (Желательно)
- [ ] Поддержать конфиг проекта, например `.language-lint.yaml`, с include/exclude paths (включаемыми/исключаемыми путями), порогами warning/fail и allowlist.
- [ ] Добавить документацию, как подключить проверку в `composer docs:validate` проекта-потребителя.
- [ ] Сделать вывод коротким: показывать только файлы, где порог превышен.

### 🟢 Could Have (Опционально)
- [ ] Поддержать отдельные пороги для `AGENTS.md`, `docs/**/*.md`, `todo/**/*.md`.
- [ ] Добавить JSON-вывод для будущей интеграции с CI.

### ⚫ Won't Have (Не будем делать)
- [ ] Не делать полноценный морфологический анализ русского и английского языков.
- [ ] Не блокировать все латинские слова: технические сущности допустимы.
- [ ] Не менять существующие валидаторы документации без отдельной интеграционной задачи.

## 4. Implementation Plan (План реализации)
1. [ ] Спроектировать формат результата анализа файла: количество слов, количество латинских слов, коэффициент, подозрительные фразы.
2. [ ] Реализовать Markdown text extractor (извлекатель текста из Markdown), который игнорирует кодовые блоки и inline code.
3. [ ] Реализовать классификацию слов и allowlist технических терминов.
4. [ ] Реализовать CLI-команду и человекочитаемый отчёт.
5. [ ] Добавить конфиг проекта с порогами и исключениями.
6. [ ] Покрыть расчёт и исключения тестами.
7. [ ] Обновить README/docs по подключению команды в проектах-потребителях.

## 5. Definition of Done (Критерии приёмки)
- [ ] CLI-команда запускается локально и анализирует заданные файлы/директории.
- [ ] Коэффициент англицизмов считается только по человекочитаемому тексту.
- [ ] Технические термины из allowlist не раздувают коэффициент.
- [ ] Для файлов с высоким коэффициентом команда показывает понятный warning.
- [ ] Тесты покрывают ключевые сценарии и проходят в `composer check`.
- [ ] Документация объясняет, как подключить проверку в проект-потребитель.

## 7. Risks and Dependencies (Риски и зависимости)
- Возможны ложные срабатывания на названия библиотек, классов и путей; для этого нужен allowlist и исключение кодовых фрагментов.
- Слишком жёсткий fail-режим может мешать внедрению; начинать нужно с warning-режима.
- Для разных проектов могут потребоваться разные пороги.
