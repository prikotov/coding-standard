# TASK-metrics-tools-evaluation: Оценка анализаторов метрик (PhpMetrics / PDepend / PhpCodeArcheology) и выбор основы

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

- Обсуждение с ChatGPT дало две стратегии: быстрый эксперимент (PhpCodeArcheology + Deptrac) и контролируемая система (PhpMetrics или PDepend + Deptrac + агрегатор + дашборд). Выбор не сделан.
- Значения LCOM, Ca, Ce у разных инструментов могут расходиться; доверять можно только после сверки на знакомых классах.
- Неизвестна совместимость кандидатов с кодом пакета (PHP 8.4: атрибуты, readonly-свойства, строгая типизация).

### Варианты или путь решения (Solution Sketch)

- Установить кандидатов как временные dev-зависимости и прогнать на src/ пакета.
- Сверить LCOM, Ca, Ce, LOC на 3–5 известных классах (например, DtoStructureSniff, ServiceStructureSniff, EnumStructureSniff, CrossModuleDomainRule).
- Оценить JSON-выход каждого: полнота полей для class-level модели (LOC/LLOC, LCOM, Ca, Ce, CC, методы/свойства).
- Зафиксировать решение: инструмент-основа (и запасной для cross-check при необходимости), обоснование, команды прогона.

### Ожидаемый результат (Expected Result)

- Таблица сравнения кандидатов (метрики, JSON, PHP 8.4, лицензия, активность) в комментариях задачи.
- Выбран инструмент-основа; решение зафиксировано в задаче и эпике.
- Временные dev-зависимости невыбранных кандидатов удалены из composer.json.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)

> Как автор эпика метрик, я хочу выбрать инструмент-основу по результатам прогона на коде этого пакета, а не по описаниям, чтобы отчёт строился на проверенных значениях LCOM/coupling и поддерживал PHP 8.4.

### Goal (Цель по SMART)

Прогнать PhpMetrics, PDepend и PhpCodeArcheology на src/ пакета, сверить LCOM, Ca, Ce, LOC на 3–5 знакомых классах, оценить JSON-выход и совместимость с PHP 8.4. Результат: выбранный инструмент-основа с обоснованием, таблица сравнения, задокументированные команды прогона. Срок: в рамках эпика EPIC-metrics-ai-maintainability.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** composer.json (временные dev-зависимости), src/ пакета (объект анализа), var/metrics/ (вывод).
- **Кандидаты:** phpmetrics/phpmetrics, pdepend/pdepend, php-code-archeology/php-code-archeology.
- **Знакомые классы для сверки:** например, DtoStructureSniff, ServiceStructureSniff, EnumStructureSniff, CrossModuleDomainRule, ServiceContractDependencyRule.
- **Текущее поведение:** метрики не собираются; инструменты не установлены.
- **Границы (Out of Scope):**
  - Не пишем агрегатор (отдельная задача TASK-metrics-aggregator).
  - Не меняем код пакета.
  - Не настраиваем Deptrac (отдельная задача TASK-metrics-module-boundaries-deptrac).
  - Не оставляем в composer.json dev-зависимости невыбранных кандидатов.

## 6. Verification (Самопроверка)

```bash
mkdir -p var/metrics

composer require --dev phpmetrics/phpmetrics:^2.10
vendor/bin/phpmetrics --report-json=var/metrics/phpmetrics.json src

composer require --dev pdepend/pdepend:^2.16
vendor/bin/pdepend --summary-xml=var/metrics/pdepend.xml src

composer config allow-plugins.php-code-archeology/php-code-archeology true
composer require --dev php-code-archeology/php-code-archeology:^2.11
printf 'y\n' | vendor/bin/phpcodearcheology \
    --report-type=json \
    --report-dir=var/metrics/code-archeology \
    src

composer remove --dev phpmetrics/phpmetrics pdepend/pdepend
```

Итоговый повторный прогон основы после подтверждения версии формул:


## 7. Risks and Dependencies (Риски и зависимости)

- PhpMetrics/PDepend могут не парсить отдельные конструкции PHP 8.4 — файлы могут выпадать из анализа (сверить количество классов в отчётах с фактическим).
- Расхождение LCOM между инструментами — ожидаемо (разные определения); критерий выбора — воспроизводимость и соответствие определениям (например, LCOM* Henderson-Sellers).
- PhpCodeArcheology — молодой инструмент; его LCOM сверять с PhpMetrics/PDepend перед доверием.
- В composer.json `minimum-stability: stable` — если кандидат доступен только в dev-ветках, это аргумент против него.
- Зависимости: нет (входная задача эпика).

### Результаты оценки

Прогон выполнен на PHP 8.4.23. Все кандидаты обработали 32 из 32 файлов `src/` без ошибок. Отдельный минимальный пример с `#[Attribute]`, `final readonly class` и продвигаемыми свойствами также разобран всеми тремя кандидатами: по два класса в каждом отчёте.

| Кандидат | Версия | Машинный формат и class-level поля | PHP 8.4 | Лицензия и активность |
|---|---:|---|---|---|
| PhpMetrics | 2.10.0 | JSON; LOC/LLOC, LCOM, Ca/Ce, CC, методы; нет количества свойств | 32/32, пример 2/2 | MIT; релиз 2026-07-21, изменения в репозитории 2026-08-02 |
| PDepend | 2.16.2 | Только XML; LOC/LLOC, Ca/Ce, WMC, методы/свойства; нет LCOM | 32/32, пример 2/2 | BSD-3-Clause; релиз 2023-12-17, изменения в репозитории 2026-08-02 |
| PhpCodeArcheology | 2.11.3 | JSON; LOC/LLOC, LCOM, `usedByCount`/`usesCount` как Ca/Ce, CC, методы и свойства | 32/32, пример 2/2 | MIT; релиз 2026-07-28, изменения в репозитории 2026-08-01 |

Сверка значений имеет формат `LOC/LLOC/LCOM/Ca/Ce/CC/методы/свойства`; `—` означает отсутствие поля. Для PDepend в позиции CC указан WMC.

| Класс | PhpMetrics | PDepend | PhpCodeArcheology |
|---|---|---|---|
| DtoStructureSniff | 122/122/2/0/2/24/9/— | 212/67/—/0/3/30/9/0 | 212/121/2/0/2/21/9/0 |
| ServiceStructureSniff | 230/205/2/0/2/43/14/— | 335/119/—/0/1/53/14/0 | 335/204/2/0/2/39/14/0 |
| EnumStructureSniff | 71/65/2/0/2/10/6/— | 120/32/—/0/1/15/6/0 | 120/64/2/0/2/9/6/0 |
| CrossModuleDomainRule | 106/72/4/0/3/28/7/— | 137/34/—/0/3/34/7/0 | 137/71/4/0/4/14/7/0 |
| ServiceContractDependencyRule | 148/99/4/0/4/12/12/— | 170/35/—/0/3/23/12/0 | 170/98/4/0/4/12/12/0 |

Расхождения ожидаемы: PhpMetrics считает `loc` не как физический диапазон строк класса, PDepend иначе определяет `lloc` и не предоставляет LCOM, а CC/WMC не взаимозаменяемы. Значения LCOM у двух кандидатов с этой метрикой совпали на всех пяти классах. PhpCodeArcheology корректно определил четыре исходящие зависимости у `CrossModuleDomainRule`, соответствующие четырём импортируемым внешним типам; PhpMetrics показал три, PDepend — три.

Дополнительный прогон выполнен на 3 592 PHP-файлах проекта `~/MyProjects/TasK/Development`. В постоянном отчёте зафиксированы первый запуск, медиана трёх запусков, пиковая память и размер отчёта для восьми инструментов. Медиана полного запуска PhpCodeArcheology составила 21,56 секунды; результат не изменил выбор основы.

Отдельно сопоставлены сбор метрик и диагностический поиск проблем. PHPMD, Phanalist и PHP Insights выводят преимущественно нарушения порогов, а не полный снимок. Для первой версии рекомендованы собственный блок `findings`, существующие проверки PHPStan и точечные сниффы сложности PHPCS/Slevomat; PHPMD оставлен возможным источником отдельных недостающих правил.

### Решение

- **Внешний эталон — PhpCodeArcheology 2.11.x.** Его JSON единственный напрямую покрывает всю требуемую class-level модель, включая количество свойств; LCOM совпал с PhpMetrics, а Ca/Ce доступны как `usedByCount`/`usesCount`.
- В `composer.json` оставлена только зависимость `php-code-archeology/php-code-archeology:^2.11` и явное разрешение Composer plugin. PhpMetrics и PDepend удалены; запасной анализатор не оставляем.
- Риски: инструмент моложе конкурентов, отчёт объёмный, а первый запуск требует подтвердить изменение формул версии 2.7.0. Агрегатор должен читать только необходимые поля и явно закрепить их семантику; первый воспроизводимый запуск использует `printf 'y\n'`.
- Собственный узкий сборщик на `nikic/php-parser` вместе с графом `Deptrac` предварительно предпочтительнее как конечная архитектура. Переключение возможно только после прототипа, сверки формул и нагрузочного прогона; до этого PhpCodeArcheology остаётся зависимостью и эталоном.
- Для поиска проблемных мест основной отчёт должен содержать отдельный неблокирующий блок `findings`; PHPMD целиком не добавляется без доказанного пробела в существующих проверках.
