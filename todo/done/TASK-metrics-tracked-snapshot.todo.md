# TASK-metrics-tracked-snapshot: актуальная структура метрик в Git

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

- Структура отчётов сейчас создаётся в временном `var/metrics/`, поэтому базовая ветка не хранит состояние метрик.
- Без сохранённой структуры PR вынужден повторно анализировать прошлую ревизию и не показывает обычный Git diff метрик рядом с изменёнными файлами.
- `var/` предназначен для временных данных и не должен становиться источником отслеживаемых артефактов проекта.

### Варианты или путь решения (Solution Sketch)

- Сохранить зеркальную JSON-структуру из `docs/conventions/ops/quality-metrics.md`, но публиковать её для Git в служебный каталог `.coding-standard/metrics/`:
  - корневой `.coding-standard/metrics/report.json`;
  - `report.json` каждого включённого каталога;
  - `{SourceFile}.php.json` каждого анализируемого PHP-файла.
- Оставить производный HTML и промежуточные файлы анализаторов в `var/metrics/`.
- Добавить режимы обновления структуры и проверки её соответствия текущему проекту.

### Ожидаемый результат (Expected Result)

- В каждой ревизии проекта хранится полное состояние метрик с тем же зеркалом путей, что и production-код.
- PR содержит локальный Git diff метрик: изменение класса видно в JSON рядом с путём его исходника, изменение агрегата — в отчётах родительских каталогов.
- CI отклоняет устаревшие, неполные или вручную отредактированные отчёты.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)

> Как ИИ-агент, проводящий код-ревью, я хочу всегда иметь актуальную структуру метрик в Git, чтобы сравнивать текущие правки с состоянием целевой ветки без повторного анализа прошлого кода.

### Goal (Цель по SMART)

Сделать JSON-структуру `.coding-standard/metrics/` каноническим отслеживаемым состоянием метрик проекта-потребителя, сохранив зеркало путей из конвенции. Команда обновления должна синхронизировать корневой, каталоговые и файловые отчёты, удалять отчёты исчезнувших исходников, а команда проверки — завершаться ошибкой при любом расхождении. Проверка: структура, созданная до коммита из подготовленных изменений, совпадает с результатом на чистом HEAD после коммита; повторный запуск не меняет файлы.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** writer зеркальных отчётов, публичный CLI, `.coding-standard.php`, init-шаблон, `.gitignore` проекта-потребителя, конвенция метрик, README и тесты.
- **Отслеживаемые артефакты:** `.coding-standard/metrics/report.json`, `.coding-standard/metrics/**/report.json`, `.coding-standard/metrics/**/*.php.json`.
- **Неотслеживаемые артефакты:** `var/metrics/index.html`, `collector.json`, `deptrac.json`, `deptrac.yaml`, `scc.json`, `scc-version.txt`, `test-stats.json`, `clover.xml` и другие промежуточные входы.
- **Единый путь для потребителей:** `.coding-standard/` принадлежит пакету и не конфликтует с предметным `metrics/`, наблюдаемостью приложения, `reports/`, `docs/` или `config/`.
- **Границы (Out of Scope):**
  - Не объединяем структуру в один lock-файл.
  - Не коммитим HTML и сырые результаты внешних инструментов.
  - Не храним несколько копий снимка внутри одной ревизии.
  - Не допускаем ручного редактирования итоговых JSON.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)

- [x] Состав и зеркало путей отслеживаемых отчётов соответствуют `docs/conventions/ops/quality-metrics.md`; корневой префикс для постоянного хранения изменён с временного `var/metrics/` на `.coding-standard/metrics/`.
- [x] Совокупность JSON содержит полную project-, module-, class- и method-level модель, findings, версии схемы и определений.
- [x] Корневой и каталоговые отчёты содержат агрегаты и ссылки на непосредственных потомков; файловый отчёт содержит типы и методы исходника.
- [x] Обновление создаёт новые отчёты и удаляет отчёты удалённых либо исключённых исходников и каталогов.
- [x] Ключи и коллекции сортируются детерминированно; пути остаются относительными и повторяют production-структуру.
- [x] Из отслеживаемых JSON исключаются время генерации, абсолютные пути и commit hash, создающий самоссылку.
- [x] Метаданные содержат версии измерителей, отпечаток конфигурации и отпечаток анализируемых входов без каталога отчётов.
- [x] Git-derived метрики учитывают подготовленные и рабочие изменения как одну будущую ревизию, чтобы снимок до коммита совпадал со снимком чистого HEAD после коммита.
- [x] Путь `.coding-standard/metrics/` фиксирован и не настраивается; `.coding-standard.php` задаёт только временный `metrics.work_dir: var/metrics`.
- [x] Прежний `report_dir` мигрирован в `work_dir` с понятной диагностикой, а `coding-standard-init` создаёт новое значение по умолчанию.
- [x] Публичная команда умеет обновить структуру и проверить её актуальность без записи.
- [x] Режим проверки возвращает ненулевой код и перечисляет созданные, изменённые и лишние отчёты.
- [x] `.gitignore` исключает временный `var/`, но не исключает канонический каталог `.coding-standard/metrics/`.
- [x] Автоматические тесты проверяют повторяемость, ручную правку, добавление, изменение, перемещение и удаление исходника.

### 🟡 Should Have (Желательно)

- [x] Git diff файлового отчёта остаётся локальным: изменение одного класса не переписывает несвязанные файловые отчёты.
- [x] `composer metrics` обновляет JSON-структуру и затем строит неотслеживаемый HTML из того же состояния.

### ⚫ Won't Have (Не будем делать)

- [ ] Не создаём `coding-standard-metrics.lock.json` или другой дублирующий единый снимок.
- [ ] Не добавляем дату генерации ради истории — историю предоставляет Git.
- [ ] Не коммитим `comparison.json`, `summary.md` и HTML: они выводятся из двух версий структуры для конкретного PR.


## 7. Risks and Dependencies (Риски и зависимости)

- В крупном проекте структура содержит много файлов; это увеличивает число отслеживаемых файлов, но делает diff локальным относительно исходников.
- Изменение формулы или конфигурации может обновить много отчётов; миграция метрик оформляется отдельно от изменения production-кода.
- Churn зависит от истории Git; алгоритм подготовленного состояния должен исключить расхождение до и после создания коммита.
- Покрытие должно собираться воспроизводимо в одинаковом окружении; нестабильные тесты делают корневой отчёт нестабильным.

- [Qodana: baseline](https://www.jetbrains.com/help/qodana/baseline.html) — снимок проекта используется для классификации новых, неизменённых и устранённых проблем.

## 9. Comments (Комментарии)

- Git хранит историю структуры, поэтому отдельная БД истории для сравнения соседних ревизий не нужна.
- `comparison.json` и `summary.md` остаются полезными производными: они интерпретируют diff двух версий структуры для ИИ-агента и человека.
- Однофайловые baseline других анализаторов обычно лежат в корне проекта. Для многофайлового зеркала выбран служебный каталог `.coding-standard/`, чтобы не занимать общее имя `metrics/` в проектах-потребителях.
