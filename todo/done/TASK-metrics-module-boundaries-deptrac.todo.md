# TASK-metrics-module-boundaries-deptrac: Полный JSON-граф Deptrac для метрик

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

- Для module-level метрик нужен полный список межмодульных зависимостей.
- Штатный JSON Deptrac содержит только нарушения, пропущенные нарушения и непокрытые зависимости; разрешённые рёбра представлены лишь общим количеством.
- Конфигурация Deptrac и карта «класс → модуль» принадлежат проекту-потребителю, например TasK, а не пакету документации.

### Варианты или путь решения (Solution Sketch)

- Добавить в пакет собственный форматтер Deptrac, который сохраняет полный список разрешённых, запрещённых, пропущенных и непокрытых рёбер с исходным и целевым классом.
- Документировать регистрацию форматтера в рекомендуемом `depfile.yaml`.
- Карту «класс → модуль» строит агрегатор TasK из его конфигурации и списка классов анализатора, а не форматтер Deptrac.

### Ожидаемый результат (Expected Result)

- Переиспользуемый форматтер полного JSON-графа Deptrac и пример его регистрации в конфигурации проекта-потребителя.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)

> Как агрегатор метрик, я хочу машинно-читаемую карту «класс → модуль» и список межмодульных зависимостей, чтобы считать module-level метрики (внутренняя/внешняя связанность, циклы, интерфейс модуля).

### Goal (Цель по SMART)

Создать переиспользуемый форматтер Deptrac полного графа зависимостей и документировать его регистрацию в `config/deptrac/depfile.yaml`. Форматтер создаёт `var/metrics/deptrac.json` на проекте-потребителе; модули определяются его собственной конфигурацией. Существующие правила `depfile.yaml` не меняются.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** src/ (форматтер полного графа), tests/ (тест форматтера), config/deptrac/README.ru.md (пример подключения).
- **Текущее поведение:** config/deptrac/depfile.yaml — шаблон consumer-проектов без форматтера метрик.
- **Границы (Out of Scope):**
  - Не меняем config/deptrac/depfile.yaml (он для consumer-проектов).
  - Не гейтим CI.
  - Не пишем агрегатор (TASK-metrics-aggregator).
  - Не анализируем vendor/.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)

- [x] Собственный форматтер на `OutputFormatterInterface` сохраняет все разрешённые, запрещённые, пропущенные и непокрытые зависимости, а не только диагностики штатного JSON.
- [x] JSON содержит исходный и целевой класс каждого ребра, тип результата и контекст; данных достаточно для инверсии графа и агрегации «модуль → модуль».
- [x] Пример регистрации форматтера и команда прогона задокументированы.

### 🟡 Should Have (Желательно)

- [ ] Сверка: количество классов в отчёте совпадает с фактическим (нет выпавших файлов).
- [ ] Отдельный модуль Tests (или обоснованное исключение) — по модели TASK-metrics-model-convention.

### ⚫ Won't Have (Не будем делать)

- [ ] Не меняем существующий config/deptrac/depfile.yaml.
- [ ] Не добавляем ruleset-ограничения (нужны только зависимости как данные, не enforcement).
- [ ] Не пишем агрегатор; собственный код ограничен форматтером полного графа.

## 4. Implementation Plan (План реализации)

- [x] Добавить универсальный форматтер `metrics-json`, который записывает все результаты Deptrac с исходным и целевым типом, слоями и контекстом.
- [x] Не включать в форматтер проектные пути, namespace и правила определения модулей.
- [x] Добавить тест формата разрешённого ребра и документацию подключения.

## 5. Definition of Done (Критерии приёмки)

- [x] Форматтер создан; прогон на проекте-потребителе выдаёт полный JSON зависимостей.
- [x] `composer validate-todo` проходит.

## 6. Verification (Самопроверка)

```bash
vendor/bin/deptrac analyse --formatter=metrics-json --output=var/metrics/deptrac.json
```

## 7. Risks and Dependencies (Риски и зависимости)

- Deptrac уже есть в require-dev (deptrac/deptrac ^2.0); собственный форматтер зависит от его программного контракта и требует теста совместимости при обновлении основной версии.
- Маппинг «класс → модуль» нельзя извлекать из форматтера: `OutputFormatterInterface` получает только рёбра. Его строит агрегатор из конфигурации и полного списка типов проекта.

- Штатный JSON Deptrac не является полным графом: он раскрывает только диагностические зависимости. Полный граф выдаёт собственный форматтер пакета; его подключает проект-потребитель.
