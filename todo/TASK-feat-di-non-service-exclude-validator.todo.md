# TASK-feat-di-non-service-exclude-validator: Проверка исключений несервисных классов из Symfony DI

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- Конвенция требует исключать сообщения и объекты данных из автоматической регистрации Symfony DI, но пакет это не проверяет.
- Из-за выборочных исключений одни `Command`, `Query` и DTO становятся сервисами, а другие нет; ошибка обнаруживается только при ручном ревью конфигурации проекта-потребителя.

### Варианты или путь решения (Solution Sketch)
- Добавить проверку модульных `services.yaml`, которая требует общие суффиксные исключения для несервисных классов.
- Дополнить её статической проверкой, запрещающей внедрение таких объектов через конструкторы сервисов, либо обоснованно выбрать другой механизм с тем же проверяемым результатом.

### Ожидаемый результат (Expected Result)
- Проект-потребитель автоматически получает понятную ошибку, если регистрирует `Command`, `Query` или DTO как сервис либо использует их как DI-зависимости.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)
> **User Story:** Как разработчик проекта-потребителя, я хочу автоматически проверять исключение сообщений и объектов данных из Symfony DI, чтобы конфигурация модулей оставалась последовательной и контейнер содержал только реальные сервисы.

### Цель по SMART (Goal)
- В рамках одной задачи добавить в `prikotov/coding-standard` воспроизводимую проверку модульной Symfony-конфигурации и ошибочного DI-внедрения `*Command`, `*Query`, `*Dto`, покрыть положительные и отрицательные сценарии тестами и включить проверку в стандартный проверочный контур пакета.

## 2. Контекст и Границы (Context and Scope)

- **Где делаем:** проверочные инструменты пакета в `bin/` и/или `src/`, их тесты в `tests/`, правила в `docs/conventions/modules/configuration.md`, подключение через Composer scripts при необходимости.
- **Текущее поведение:** конвенция уже требует суффиксные `exclude`, но автоматической проверки конфигурации и DI-зависимостей нет.
- **Границы (Out of Scope):** массовое исправление проектов-потребителей, изменение Symfony DI, бизнес-кода или публичных CQRS-контрактов.

## 7. Риски и зависимости (Risks and Dependencies)

- YAML допускает несколько эквивалентных форм ресурсов и исключений; проверка не должна сравнивать конфигурацию только как текст.
- Постфикс `Command` используется также Symfony console-командами, поэтому правило обязано учитывать слой и путь.
- Проверка скомпилированного контейнера может потребовать необязательной интеграции с Symfony; предпочтителен механизм без новой обязательной зависимости.

## 9. Результат (Result)

Реализовано в ветке `task/di-non-service-exclude-validator`:

- Новая команда `vendor/bin/coding-standard-di-check` (bin + `src/Di/`):
  - проверяет каждый авто-импорт `resource` в модульных `services.yaml` на общие суффиксные маски `*Dto.php`, `*Event.php`, `*Exception.php`, `*Enum.php`, `*Vo.php`, Application `*Command.php`/`*Query.php`; выборочные исключения отдельных файлов и каталогов отклоняются (виртуальные probe-файлы);
  - статически обнаруживает внедрение несервисных классов в конструкторы потенциальных сервисов через php-parser (`NameResolver`); классы, исключённые из контейнера своими же exclude-паттернами (например `Domain/Entity`), не проверяются;
  - Symfony YAML парсится структурно (`symfony/yaml`, `PARSE_CUSTOM_TAGS`), параметры `%param%` и относительные пути резолвятся;
  - Symfony console `Command` вне `Application\UseCase\Command` не затрагивается;
  - требования exclude различают типы модулей: Common — обязательный минимум конвенции независимо от содержимого; модули приложений и корневые импорты `apps/*` — маски для типов, фактически присутствующих в дереве (требование включается вместе с первым классом типа); импорты из `vendor/` не проверяются.
  - несервисные presentation-типы `*FormModel.php` (данные форм) и `*Constraint.php` (кастомные правила Symfony Validator) — evidence-категории только для модулей приложений и корневых импортов `apps/*` (Presentation-слой): маска требуется, когда такие классы реально есть; появление такого класса в Common-модуле — отдельная ошибка слоистости с требованием перенести класс в модуль приложения, а не маскировать; обязательный минимум Common-модулей не расширен; внедрение их в конструкторы флагается аналогично остальным несервисным классам;
  - evidence-скан учитывает только классы, не исключённые этим же импортом: корневой импорт приложения, исключивший `Module/`, не получает требований по классам модулей;
- Интеграция: `coding-standard-init` добавляет команду в `make check` рядом с `coding-standard-verify`; таблица CLI и раздел README; подраздел конвенции `docs/conventions/modules/configuration.md`.
- Тесты: 22 e2e-сценариев из корня изолированного проекта-потребителя + 10 юнит-тестов GlobMatcher (`tests/Di/`), обновлённые тесты init.
- Проверено на реальных проектах: `stocks2` (исходный кейс модуля TInvest) и `TasK/Development` — выявлены фактические отставания модульных конфигов от конвенции. После правок по ревью: ложные требования масок для отсутствующих типов сняты (TasK 317→153, stocks2 194→125): presentation-маски — только для `apps/*`-импортов, evidence не требует масок для классов, уже исключённых этим же импортом (корневые импорты `../src/` с `exclude: ../src/Module/`), реальные дыры остаются — TasK модуль Webhook без маски `*Constraint.php`, stocks2 web-модули без маски `*FormModel.php`, корневые импорты без масок для `Component/*Dto.php`; корректные конфиги модулей приложений проходят.

- `*Constraint.php` — кастомные правила Symfony Validator (`#[Attribute]`-классы, наследующие `Symfony\Component\Validator\Constraint`): валидатор инстанцирует их сам, сервисами им быть не нужно.
