# TASK-metrics-report-diff: детерминированное сравнение снимков метрик

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

- Каноническая JSON-структура `.coding-standard/metrics/` хранит состояние проекта в одной ревизии, но обычный Git diff не объясняет направление каждой метрики.
- Абсолютное значение метрики не показывает, улучшили или ухудшили текущие правки кодовую базу.
- ИИ-агенту приходится сопоставлять большие JSON-файлы самостоятельно, поэтому результат ревью не воспроизводится.

### Варианты или путь решения (Solution Sketch)

- Принимать две готовые версии отслеживаемой структуры: базовой ветки (`baseline`) и текущих правок (`current`).
- Проверять совместимость схемы, определений метрик, конфигурации анализа и версий инструментов до сравнения.
- Сопоставлять проект, модули, классы и методы по стабильным идентификаторам.
- Формировать детерминированные `comparison.json` и краткий `summary.md` без временных полей.

### Ожидаемый результат (Expected Result)

- Одинаковые снимки всегда дают одинаковый файл сравнения.
- ИИ-агент видит улучшения, ухудшения, добавленные и удалённые объекты без повторного вычисления дельты.
- Рост проекта и появление нового кода отделены от регрессии существующих объектов.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)

> Как ИИ-агент, проводящий код-ревью, я хочу получить точное изменение метрик между базовой веткой и текущими правками, чтобы учитывать направление изменения качества при решении о прохождении ревью.

### Goal (Цель по SMART)

Добавить публичную CLI-команду сравнения двух каталогов `.coding-standard/metrics/`. Команда должна рекурсивно проверить полноту и совместимость входов и создать стабильный машиночитаемый отчёт с дельтами на уровнях проекта, модуля, класса и метода. Проверка: порядок обхода файлов и перестановка ключей входного JSON не меняют результат, повторный запуск даёт идентичный файл, несовместимые снимки завершаются ошибкой с указанием причины.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** публичный CLI пакета, схема отчёта, классы сравнения, тесты и документация модели метрик.
- **Входы:** две версии отслеживаемой JSON-структуры `.coding-standard/metrics/` из базовой и текущей ревизий одного проекта.
- **Выходы:** полный JSON для инструмента и короткий Markdown для человека и PR.
- **Границы (Out of Scope):**
  - Не выполняем checkout Git и не запускаем сбор снимков в этой задаче.
  - Не публикуем артефакты в GitHub или другой системе ревью.
  - Не заменяем анализ кода и конвенций одним числовым баллом.
  - Не считаем увеличение общего LOC, количества классов или методов автоматической регрессией.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)

- [x] Публичная команда принимает явные пути `baseline`, `current` и каталог результата.
- [x] Команда рекурсивно читает только канонические корневой, каталоговые и файловые отчёты, игнорируя HTML и промежуточные файлы.
- [x] Снимок содержит версии схемы и определений метрик, отпечатки конфигурации и входов, а также версии источников данных.
- [x] До сравнения проверяются проект, схема, определения метрик и отпечаток конфигурации; несовместимость возвращает ненулевой код и перечисляет различия.
- [x] Объекты сопоставляются по стабильным идентификаторам, а результат отдельно содержит `added`, `removed`, `changed` и `unchanged_count`.
- [x] Для изменённых числовых метрик сохраняются `before`, `after`, `delta` и направление `improved`, `regressed` или `neutral` согласно версии определения метрики.
- [x] Метрики без однозначного направления, включая общий LOC и churn, помечаются как информационные и не создают регрессию сами по себе.
- [x] Новые и удалённые объекты не маскируются агрегированной дельтой проекта.
- [x] Выход сортируется детерминированно и не содержит времени запуска или абсолютных путей.
- [x] Создаются `comparison.json` для ИИ-агента и `summary.md` с изменениями в изменённой области.
- [x] Unit- и интеграционные тесты покрывают улучшение, ухудшение, нейтральную метрику, добавление, удаление и несовместимые входы.

### 🟡 Should Have (Желательно)

- [x] Команда принимает список изменённых Git-путей и помечает объекты, относящиеся к текущему diff.
- [x] Резюме ограничивает объём и показывает первые причины регрессии со ссылками на объект и файл.

### ⚫ Won't Have (Не будем делать)

- [ ] Не вводим универсальный интегральный балл качества.
- [ ] Не задаём пакетные абсолютные пороги для всех проектов.
- [ ] Не храним историю нескольких сравнений.

## 7. Risks and Dependencies (Риски и зависимости)

- Переименование или перемещение объекта выглядит как удаление и добавление; автоматическое распознавание rename не требуется в первой версии.
- Изменение конфигурации или формулы метрики делает снимки несопоставимыми и требует новой базовой линии.
- Не у каждой метрики есть однозначное направление качества; такие значения должны оставаться информационными.
