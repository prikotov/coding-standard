# TASK-metrics-report-diff: детерминированное сравнение снимков метрик

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

- `report.json` показывает состояние проекта только в одной точке.
- Абсолютное значение метрики не показывает, улучшили или ухудшили текущие правки кодовую базу.
- ИИ-агенту приходится сопоставлять большие JSON-файлы самостоятельно, поэтому результат ревью не воспроизводится.

### Варианты или путь решения (Solution Sketch)

- Принимать два готовых снимка: базовой ветки (`baseline`) и текущих правок (`current`).
- Проверять совместимость схемы, определений метрик, конфигурации анализа и версий инструментов до сравнения.
- Сопоставлять проект, модули, классы и методы по стабильным идентификаторам.
- Формировать детерминированные `comparison.json` и краткий `summary.md` без временных полей.

### Ожидаемый результат (Expected Result)

- Одинаковые снимки всегда дают одинаковый файл сравнения.
- ИИ-агент видит улучшения, ухудшения, добавленные и удалённые объекты без повторного вычисления дельты.
- Рост проекта и появление нового кода отделены от регрессии существующих объектов.

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)

> Как ИИ-агент, проводящий код-ревью, я хочу получить точное изменение метрик между базовой веткой и текущими правками, чтобы учитывать направление изменения качества при решении о прохождении ревью.

### Goal (Цель по SMART)

Добавить публичную CLI-команду сравнения двух `report.json`. Команда должна проверить совместимость входов и создать стабильный машиночитаемый отчёт с дельтами на уровнях проекта, модуля, класса и метода. Проверка: перестановка ключей входного JSON не меняет результат, повторный запуск даёт идентичный файл, несовместимые снимки завершаются ошибкой с указанием причины.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** публичный CLI пакета, схема отчёта, классы сравнения, тесты и документация модели метрик.
- **Входы:** два снимка, собранные `coding-standard-metrics` для базовой и текущей ревизий одного проекта.
- **Выходы:** полный JSON для инструмента и короткий Markdown для человека и PR.
- **Границы (Out of Scope):**
  - Не выполняем checkout Git и не запускаем сбор снимков в этой задаче.
  - Не публикуем артефакты в GitHub или другой системе ревью.
  - Не заменяем анализ кода и конвенций одним числовым баллом.
  - Не считаем увеличение общего LOC, количества классов или методов автоматической регрессией.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)

- [ ] Публичная команда принимает явные пути `baseline`, `current` и каталог результата.
- [ ] Снимок содержит версии схемы и определений метрик, отпечаток конфигурации анализа, commit и версии источников данных.
- [ ] До сравнения проверяются проект, схема, определения метрик и отпечаток конфигурации; несовместимость возвращает ненулевой код и перечисляет различия.
- [ ] Объекты сопоставляются по стабильным идентификаторам, а результат отдельно содержит `added`, `removed`, `changed` и `unchanged_count`.
- [ ] Для изменённых числовых метрик сохраняются `before`, `after`, `delta` и направление `improved`, `regressed` или `neutral` согласно версии определения метрики.
- [ ] Метрики без однозначного направления, включая общий LOC и churn, помечаются как информационные и не создают регрессию сами по себе.
- [ ] Новые и удалённые объекты не маскируются агрегированной дельтой проекта.
- [ ] Выход сортируется детерминированно и не содержит времени запуска или абсолютных путей.
- [ ] Создаются `comparison.json` для ИИ-агента и `summary.md` с изменениями в изменённой области.
- [ ] Unit- и интеграционные тесты покрывают улучшение, ухудшение, нейтральную метрику, добавление, удаление и несовместимые входы.

### 🟡 Should Have (Желательно)

- [ ] Команда принимает список изменённых Git-путей и помечает объекты, относящиеся к текущему diff.
- [ ] Резюме ограничивает объём и показывает первые причины регрессии со ссылками на объект и файл.

### ⚫ Won't Have (Не будем делать)

- [ ] Не вводим универсальный интегральный балл качества.
- [ ] Не задаём пакетные абсолютные пороги для всех проектов.
- [ ] Не храним историю нескольких сравнений.

## 4. Implementation Plan (План реализации)

1. [ ] Зафиксировать контракт совместимости и схему `comparison.json` в конвенции метрик.
2. [ ] Добавить недостающие метаданные и отпечаток конфигурации в снимок.
3. [ ] Реализовать сопоставление объектов и классификацию изменений метрик.
4. [ ] Добавить CLI и генерацию детерминированных JSON/Markdown.
5. [ ] Покрыть контракт тестами и проверить на двух ревизиях TasK.

## 5. Definition of Done (Критерии приёмки)

- [ ] Два совместимых снимка сравниваются одной публичной командой.
- [ ] Повторный запуск даёт байт-в-байт одинаковые `comparison.json` и `summary.md`.
- [ ] Несовместимые снимки не сравниваются молча.
- [ ] ИИ-агенту не требуется самостоятельно вычислять дельты исходных JSON.
- [ ] `composer check` зелёный.

## 6. Verification (Самопроверка)

```bash
vendor/bin/coding-standard-metrics-compare \
  --baseline=var/metrics/baseline/report.json \
  --current=var/metrics/current/report.json \
  --output=var/metrics/review
test -s var/metrics/review/comparison.json
test -s var/metrics/review/summary.md
composer check
```

## 7. Risks and Dependencies (Риски и зависимости)

- Переименование или перемещение объекта выглядит как удаление и добавление; автоматическое распознавание rename не требуется в первой версии.
- Изменение конфигурации или формулы метрики делает снимки несопоставимыми и требует новой базовой линии.
- Не у каждой метрики есть однозначное направление качества; такие значения должны оставаться информационными.

## 9. Comments (Комментарии)

- Главная единица анализа PR — изменение метрики, а не её абсолютное значение.
