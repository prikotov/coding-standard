# TASK-metrics-model-convention: Модель метрик качества (class-level и module-level) в docs/conventions/

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

- Нет зафиксированной модели метрик: что считать на уровне «метод → класс» и «класс → модуль», как агрегировать, что такое модуль и «компонент».
- Средний LCOM классов не является cohesion модуля — нужна отдельная графовая метрика (требование из обсуждения).
- ИИ-агенты не имеют инструкции, как интерпретировать числа отчёта.

### Варианты или путь решения (Solution Sketch)

- Новый документ-правило (type: rule) в docs/conventions/ops/ (например, quality-metrics.md): уровни метрик, определения, агрегация, интерпретация, определение модуля (предметный компонент пакета; слои — внутренние).
- Обновить docs/conventions/index.md (секция «Операционные практики»).
- Опираться на результаты TASK-metrics-tools-evaluation (какие метрики даёт выбранный инструмент).

### Ожидаемый результат (Expected Result)

- Документ-правило «Метрики качества» с моделью: class-level (LOC/LLOC, методы/свойства, LCOM, Ca/Ce, CC, churn, модуль) и module-level (количество классов/файлов, суммарный LOC, медиана/макс/p90/p95 размера класса, медиана/макс LCOM, внутренние/входящие/исходящие зависимости, доля внешних зависимостей, циклы, размер публичного интерфейса, churn).
- Определение модуля и «компонента» (пара класс-метод / модуль-класс).
- Раздел «как читать отчёт ИИ-агенту» (какие значения — красные флаги).

## 1. Concept and Goal (Концепция и Цель)

### Story (User Story)

> Как ИИ-агент, я хочу единую задокументированную модель метрик с определениями и интерпретацией, чтобы одинаково оценивать поддерживаемость проекта по отчёту.

### Goal (Цель по SMART)

Создать документ-правило в docs/conventions/ (type: rule, категория ops): модель метрик на уровнях «метод → класс» и «класс → модуль» (cohesion, coupling, размер, количество компонентов), определение модуля как предметного компонента, правила агрегации (включая графовую cohesion модуля вместо среднего LCOM), интерпретацию значений для ИИ-агентов. Обновить index.md. Проверка: `composer validate-docs` и `composer validate-todo` проходят.

## 2. Context and Scope (Контекст и Границы)

- **Где делаем:** docs/conventions/ops/quality-metrics.md (новый файл), docs/conventions/index.md (добавить ссылку).

  - Не описываем метрики, которые нельзя получить выбранным инструментом + Deptrac + git (иначе модель нереализуема).

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)

- [ ] Документ-правило с front matter (name, type: rule, description) по шаблону конвенций пакета.
- [ ] Модель class-level: LOC/LLOC, количество методов и свойств, LCOM, Ca/Ce (или CBO), CC, churn, принадлежность модулю.
- [ ] Модель module-level: количество классов и файлов, суммарный LOC, медианный и максимальный размер класса, p90/p95, медианный и максимальный LCOM, внутренние зависимости, входящие/исходящие межмодульные зависимости, доля зависимостей, покидающих модуль, число циклов, размер публичного интерфейса, churn модуля.
- [ ] Явное правило: cohesion модуля — графовая метрика (доля внутренних зависимостей), средний LCOM не является cohesion модуля.
- [ ] Определение модуля (предметный компонент пакета; слои внутри модуля) и «компонента» (пара класс-метод / модуль-класс).
- [ ] Обновлён docs/conventions/index.md; `composer validate-docs` проходит.

### ⚫ Won't Have (Не будем делать)

- [ ] Не автоматизируем сбор метрик (отдельные задачи эпика).
- [ ] Не меняем существующие конвенции.
